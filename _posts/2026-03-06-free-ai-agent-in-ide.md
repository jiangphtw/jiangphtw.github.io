> 本文截圖與操作畫面以 **2026 年 3 月 11 日** 為準。GitHub Copilot 與 Antigravity 的可用模型、介面名稱、配額與申請流程之後都可能調整。

如果寫程式時仍習慣將一段程式碼複製到瀏覽器中的聊天機器人，取得回答後再貼回 IDE，便很容易陷入效率較低的工作流程。

這種方式仍然可行，但存在幾個明顯問題：

- AI 只能看到貼入對話的幾段內容，無法掌握整個專案。
- AI 通常不知道這段程式碼還依賴哪些檔案、型別與設定。
- 使用者必須自行補充上下文，反覆複製與貼上。
- 對話與專案彼此分離，難以持續保留完整的專案脈絡。
- 真正修改檔案時，仍須自行將結果套用回專案。

因此，我現在更偏好直接在 **IDE 中使用 AI Agent**。

這樣做不只是減少幾次複製貼上，更改變了整體協作模式。AI 不再只是聊天室中的問答工具，而是能直接讀取目前工作區、理解多個檔案之間的關係、提出修改建議，甚至產生 diff 的協作者。

這也是本文想討論的重點：**真正好用的 AI，不是自動執行最多工作的工具，而是最適合與人協作的工具。**

---

# 1. 為什麼我更推薦在 IDE 中使用 AI Agent

我最在意的不是 AI 能否一次完成所有工作，而是它能否在真實專案中維持可控的協作節奏。

在 IDE 中使用 AI Agent，通常有以下幾項明顯優勢：

- **不必再移動程式碼**
  AI 已整合於開發環境中，不必手動將檔案內容貼到瀏覽器。

- **可以讀取更完整的上下文**
  AI 不只查看單一函式，還能一併理解匯入關係、型別、設定檔與相依模組。

- **比較容易保留工作脈絡**
  持續在同一個工作區與專案中處理相關任務，比瀏覽器聊天室更接近連貫的協作方式。

- **可以清楚查看修改內容**
  這點非常重要。修改會直接顯示於 IDE 中，使用者可以查看 diff、逐段審查，再決定是否接受。

- **更容易落實 Human-in-the-loop（人類參與決策）**
  使用者不是將決策完全交給 AI，而是讓 AI 先閱讀、提出方案並產生草稿，最後再由人批准、修改或退回。

這並不是說 CLI 工具或獨立應用程式沒有價值。它們很適合某些快速操作、一次性任務或 Shell 工作流程。不過，面對持續演進的專案時，**透明度、可審查性，以及對多檔案上下文的掌握**，往往比全自動執行更重要。

基於上述原因，我更偏好將 AI 整合至 IDE，而不是將專案內容搬到外部 AI 工具中。

# 2. 方法一：GitHub Copilot Education + VS Code

如果具備學生或教師身分，**GitHub Education + GitHub Copilot + VS Code** 是很值得優先考慮的方案。

這項方案的優點相當明確：

- 許多開發者原本就在使用 GitHub 和 VS Code。
- 申請通過後，可以直接在熟悉的 IDE 中開始工作。
- 對一般開發者來說，VS Code 的檔案樹、版本控制、編輯器、終端機與擴充套件生態都已經很成熟。
- 使用者可以在同一處查看 prompt、程式碼、diff 與 Git 變更。

## 2.1 從 GitHub 設定進入 Education Benefits

先進入 GitHub 個人設定頁面，再從左側選單找到 `Billing and licensing`。

![GitHub 設定中的 Billing and licensing](/assets/images/260311/1.PNG)

_從 GitHub 設定頁面的左側選單進入 `Billing and licensing`。_

展開選單後，可以在下方看到 `Education benefits`。

![Billing and licensing 底下的 Education benefits](/assets/images/260311/2.PNG)

_展開 `Billing and licensing` 後，進入 `Education benefits`。_

## 2.2 送出 GitHub Education 驗證

進入 GitHub Education 頁面後，點選驗證或重新驗證按鈕，即可開始申請流程。

![GitHub Education 頁面中的驗證入口](/assets/images/260311/3.PNG)

_進入 GitHub Education 後，從右下角的驗證入口開始申請。_

接著，系統會引導申請者完成以下步驟：

1. 驗證學校信箱。
2. 選擇學校及教育身分。
3. 提供位置資訊，讓系統確認申請者是否位於校園周邊。
4. 上傳相關證件，進行人工審核。

![Education Benefits Application 驗證流程畫面](/assets/images/260311/4.PNG)

_實際申請時，通常會要求學校信箱、位置資訊與證件資料。_

以我的經驗來看，整個流程並不複雜，但送出申請後不會立即通過。較合理的預期是**大約一週內完成審核**。如果學校網域、證件資訊與位置資料都很明確，審核通常會更順利。

## 2.3 在 VS Code 連結 GitHub 帳號

Education 資格通過後，下一步是在 VS Code 中登入 GitHub 帳號。

![在 VS Code 中登入 GitHub 帳號](/assets/images/260311/5.PNG)

_從 VS Code 右上角的帳號區登入 GitHub，讓 Copilot 對應至已通過的資格。_

完成這一步後，便能直接在日常編輯環境中使用 Copilot 的聊天、程式碼補全與代理式互動等功能，不必再切換至瀏覽器。

## 2.4 可直接使用多家主流模型

這項方案最具吸引力的一點，是不必分別訂閱每一家模型公司的服務。依我在 **2026 年 3 月 11 日** 看到的介面，GitHub Copilot 已可選用不同公司提供的模型。

![GitHub Copilot 中可選用的模型列表](/assets/images/260311/6.PNG)

_截圖中的介面列出了 Claude、Gemini、GPT 與 Grok 等不同系列的模型。_

這種做法的價值不只在於免費，也在於能夠在同一套 IDE 工作流程中，根據任務需求切換模型：

- 需要快速補全或輕量協助時，可以選用回應速度較快的模型。
- 需要讀取較長上下文、整理架構或推理複雜修改時，可以選用能力較強的模型。
- 要求模型直接修改專案檔案時，也能立即在本機檢查結果。

對我而言，這比在瀏覽器中開啟多個聊天視窗，再手動比較回答，更加實用。

# 3. 方法二：Antigravity

如果不打算申請 GitHub Education，另一個可以考慮的方案是 **Antigravity**。

Antigravity 以 VS Code 的開放原始碼版本為基礎開發，因此介面容易上手，整體操作邏輯也與 VS Code 相近。換句話說，原本熟悉 VS Code 的使用者不需要付出太高的轉換成本。

![Antigravity 的整體介面](/assets/images/260311/7.PNG)

_Antigravity 的整體介面與 VS Code 相近，可以同時顯示工作區與 Agent 面板。_

連結 Google 帳號後即可開始使用。相較於 GitHub Education 的申請流程，這項方案的門檻低得多；如果只是想先體驗在 IDE 中使用 AI Agent，Antigravity 是相當直接的選擇。

另一項特色是，Antigravity 不會將使用者導向純聊天應用程式，而是保留 IDE 的工作介面：

- 左側顯示檔案與工作區。
- 中央保留熟悉的編輯區。
- 右側則顯示 Agent 對話與工作面板。

這項版面配置很重要，因為它讓 AI 直接融入開發環境，而不是成為與專案分離的外部工具。

## 3.1 Antigravity 中可用的免費模型

依我在 **2026 年 3 月 11 日** 看到的介面，Antigravity 也提供數個可直接使用的模型選項。

![Antigravity 中可選用的模型列表](/assets/images/260311/8.PNG)

_截圖中的介面列出了 Gemini、Claude 與 GPT-OSS 等模型選項。_

截圖當時顯示的選項包括：

- `Gemini 3.1 Pro (High)`
- `Gemini 3.1 Pro (Low)`
- `Gemini 3 Flash`
- `Claude Sonnet 4.6 (Thinking)`
- `Claude Opus 4.6 (Thinking)`

對一般開發任務而言，這些模型已足以協助完成多項工作，例如：

- 閱讀陌生程式碼並解釋架構。
- 跨越多個檔案尋找錯誤。
- 先產出重構方案，再逐步修改。
- 協助補充測試、註解與文件。

如果目標是先建立一套讓 AI 能在 IDE 中共同檢視專案的工作流程，而不是限定使用某一家模型供應商，Antigravity 確實是值得嘗試的免費方案。

# 4. 如何選擇這兩種方案

比較 GitHub Copilot Education + VS Code 與 Antigravity 後，可以整理出以下差異：

| 方案 | 主要門檻 | 優勢 | 適合對象 |
| --- | --- | --- | --- |
| GitHub Copilot Education + VS Code | 需要學生或教師資格，且要先完成 GitHub Education 審核 | 生態成熟、直接整合 GitHub 與 VS Code、可在熟悉環境中協作 | 已經在用 GitHub 與 VS Code，且具備教育身分的人 |
| Antigravity | 只要能登入帳號即可開始，進入成本較低 | 上手快、介面接近 VS Code、能快速體驗 IDE 內 Agent 協作 | 想先用最低成本開始，或沒有 GitHub Education 資格的人 |

如果具備學生身分，而且平常主要使用 VS Code，我會優先推薦 **GitHub Copilot Education**，因為它能將 AI 直接整合至既有的開發流程。

如果目前不具備教育資格，或只是想先體驗在 IDE 中與 AI Agent 協作的差異，**Antigravity** 會是更快的入門選擇。

# 5. 我最推薦的用法：將 AI 視為協作者，而非自動駕駛

本文最重要的目的，不是比較哪項工具更新穎，而是提醒讀者一件事：

**最穩健的使用方式，仍然是 Human-in-the-loop（人類參與決策）。**

也就是說，AI 可以閱讀、分析、提出方案並產生修改內容，但最終決策權必須保留給人。以下是我認為較穩健的工作流程：

1. **先請 AI 閱讀，不要急著修改**
   先讓 AI 閱讀相關檔案，說明模組關係、資料流向與可能風險。

2. **先請 AI 提出計畫，再開始修改**
   要求 AI 先列出預計修改的檔案、修改方式與可能的副作用。

3. **限制 AI 的修改範圍**
   例如只允許修改兩個指定檔案，或先進行最小可行修改。

4. **查看 diff，再決定是否接受**
   這也是 IDE 方案的主要優勢。使用者看到的不是抽象回答，而是具體變更。

5. **自行執行測試並完成最後的 commit**
   AI 可以提供協助，但開發者仍須承擔最終責任。

也可以建立以下 prompt 使用習慣：

- `先不要改 code，先讀目前 workspace 中與登入流程相關的檔案，整理依賴關係給我。`
- `先提出修改計畫，列出預計變更的檔案與原因。`
- `只修改這兩個檔案，其餘檔案不要動。`
- `修改後請用條列說明每一處變更的理由。`

這種用法並非為了逃避工作，而是將 AI 轉變成一個**可以接受審查的協作者**。

# 6. 哪些情境最適合在 IDE 中使用 AI Agent

我認為以下幾種情境特別適合：

- **接手陌生專案時**
  先讓 AI 協助整理進入點、模組關係與重要相依項目。

- **要做小功能或局部重構時**
  先請 AI 提出修改方案，再由開發者決定採用哪一種。

- **要補測試時**
  這類工作通常脈絡清楚、規則固定，很適合先由 AI 產生草稿。

- **要補文件、註解、README 時**
  AI 很適合協助整理既有內容。

- **要找跨檔案 bug 時**
  當問題橫跨多個模組時，IDE 中的上下文整合能力通常比瀏覽器聊天工具更方便。

相反地，如果完全不查看 diff、不執行測試，也不確認推論是否合理，再強大的 AI Agent 都可能造成更多問題。

# 7. 結語

對我而言，AI 最有價值的角色，不是在瀏覽器中充當擅長對話的機器人，也不是在 CLI 中盲目執行所有指令，而是**進入 IDE，成為能閱讀專案、提出修改並接受審查的協作者**。

這也是我特別推薦這兩種免費方案的原因：

- 有教育資格，就走 **GitHub Copilot Education + VS Code**。
- 想快速開始，就試試 **Antigravity**。

真正值得追求的不是讓 AI 取代開發者，而是建立更完善的協作流程：

- AI 負責快速閱讀、整理資訊並產生草稿。
- 人負責判斷、取捨、驗證與最終決策。

這樣的組合更接近真正可持續的開發方式。
