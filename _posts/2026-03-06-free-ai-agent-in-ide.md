> 本文截圖與操作畫面以 **2026 年 3 月 11 日** 為準。GitHub Copilot 與 Antigravity 的可用模型、介面名稱、配額與申請流程之後都可能調整。

如果你現在寫程式時，還是習慣把一段 code 複製到瀏覽器中的聊天機器人，問完之後再把答案貼回 IDE，那其實很容易在一開始就掉進一個效率不高的工作流。

這種方式不是完全不能用，但它有幾個很明顯的問題：

- AI 只看得到你貼上去的那幾段內容，看不到整個專案。
- 它常常不知道這段程式碼還依賴哪些檔案、哪些型別、哪些設定。
- 你必須一直自己搬運上下文，來回複製貼上。
- 對話和專案是分離的，久了之後沒有真正的「專案記憶」。
- 真正要改檔時，你還是得自己把結果重新套回去。

所以我現在更偏好的方式，是直接在 **IDE 裡使用 AI Agent**。

這樣做的差異，不只是少了幾次複製貼上而已，而是整個合作模式都變了。AI 不再只是聊天室裡的一個回答機器，而是變成一個能直接讀取目前工作區、理解多個檔案關係、提出修改建議，甚至直接幫你產生 diff 的協作者。

這也是我這篇文章想談的重點：**真正好用的 AI，不是最會自動動手的那個，而是最適合跟人一起協作的那個。**

# 1. 為什麼我更推薦在 IDE 裡用 AI Agent

我最在意的不是「AI 能不能一次把東西全做完」，而是它能不能在一個真實專案裡，跟我維持可控的合作節奏。

在 IDE 裡使用 AI Agent，通常有幾個明顯優勢：

- **不用再搬運程式碼**  
  AI 就在開發環境裡，不需要把檔案內容手動貼去瀏覽器。

- **可以讀到更完整的上下文**  
  它不只看單一函式，還能沿著 import、型別、設定檔、相依模組一起理解。

- **比較容易保留工作記憶**  
  同一個工作區、同一個專案、同一串任務脈絡，比起瀏覽器聊天室更接近真正的協作。

- **你看得見它改了什麼**  
  這點非常重要。因為修改會回到 IDE 裡，你可以直接看 diff、逐段 review、決定要不要接受。

- **Human in the loop 比較容易成立**  
  你不是把決策丟給 AI，而是讓 AI 先讀、先提案、先生成草稿，最後由你批准、修改或退回。

我不是說 CLI 工具或獨立 app 沒有價值。它們在某些快速操作、一次性任務、或 shell workflow 裡確實很好用。但如果你面對的是一個真的會持續演化的專案，那麼 **透明度、可審查性、以及對多檔案上下文的掌握**，往往比「全自動執行」更重要。

也因為這樣，我更偏好把 AI 放進 IDE 裡，而不是把專案搬去 AI 那裡。

# 2. 方法一：GitHub Copilot Education + VS Code

如果你有學生或教師身分，第一條非常值得走的路，是 **GitHub Education + GitHub Copilot + VS Code**。

這條路線的優點很明確：

- 你本來就很可能已經在用 GitHub 和 VS Code。
- 申請通過後，可以直接在熟悉的 IDE 裡開始工作。
- 對一般開發者來說，VS Code 的檔案樹、版本控制、編輯器、終端機與擴充套件生態都已經很成熟。
- 你可以在同一個地方看 prompt、看程式碼、看 diff、看 git 變更。

## 2.1 從 GitHub 設定進入 Education Benefits

先到 GitHub 個人設定頁面，左側找到 `Billing and licensing`。

![GitHub 設定中的 Billing and licensing](/assets/images/260311/1.PNG)

_先從 GitHub 設定左側進入 `Billing and licensing`。_

展開之後，可以在底下看到 `Education benefits`。

![Billing and licensing 底下的 Education benefits](/assets/images/260311/2.PNG)

_展開 `Billing and licensing` 後，進入 `Education benefits`。_

## 2.2 送出 GitHub Education 驗證

進到 GitHub Education 頁面後，點選驗證或重新驗證按鈕，就可以開始申請流程。

![GitHub Education 頁面中的驗證入口](/assets/images/260311/3.PNG)

_進入 GitHub Education 後，從右下角的驗證入口開始申請。_

接著系統會引導你完成幾個步驟：

1. 驗證學校信箱。
2. 選擇學校或教育身分。
3. 分享位置，確認你是不是在校園周邊。
4. 上傳相關證件，進行人工審核。

![Education Benefits Application 驗證流程畫面](/assets/images/260311/4.PNG)

_實際申請時，通常會要求學校信箱、位置資訊與證件資料。_

以我自己的經驗，整個流程不算複雜，但也不是按完當下就立即通過。比較合理的預期是，**大約一週內完成審核**。如果你的學校網域、證件資訊或定位條件比較明確，通常會順一些。

## 2.3 在 VS Code 連結 GitHub 帳號

Education 資格通過之後，下一步就是在 VS Code 裡登入你的 GitHub 帳號。

![在 VS Code 中登入 GitHub 帳號](/assets/images/260311/5.PNG)

_在 VS Code 右上角帳號區登入 GitHub，讓 Copilot 能綁定到你的資格。_

這一步完成後，Copilot 的聊天、補全、代理式互動等能力就可以直接回到你的日常編輯環境裡，不需要再切到瀏覽器。

## 2.4 可直接使用多家主流模型

這條路線最有吸引力的一點，是你不需要為了每一家模型公司分別再訂一次服務。以我 **2026 年 3 月 11 日** 的畫面來看，GitHub Copilot 裡就已經能選到來自不同公司的模型。

![GitHub Copilot 中可選用的模型列表](/assets/images/260311/6.PNG)

_以我截圖當下的畫面為例，可以看到 Claude、Gemini、GPT、Grok 等不同系列模型。_

這種做法的價值，不只是「免費」，而是你可以在同一個 IDE 工作流裡根據任務切換模型：

- 要快速補全或做輕量協助，用偏快的模型。
- 要讀較長上下文、整理架構或推理較複雜的修改，用能力更強的模型。
- 要求它直接在專案裡改檔時，你也能在本地立刻檢查結果。

對我來說，這比在瀏覽器開一排不同聊天視窗，再手動測試哪個回答比較好，實際太多了。

# 3. 方法二：Antigravity

如果你不想走 GitHub Education 這條路，另一個可以考慮的方向是 **Antigravity**。

它的介面之所以容易上手，是因為它本身就是基於 VS Code 開源版本修改出來的，因此整體操作邏輯很接近 VS Code。換句話說，如果你本來就習慣 VS Code，切過去的成本不高。

![Antigravity 的整體介面](/assets/images/260311/7.PNG)

_Antigravity 的整體介面與 VS Code 很接近，工作區與 Agent 面板可以同時存在。_

你只要連接 Google 帳號，就可以開始使用。這個門檻比起 GitHub Education 申請流程低很多，所以如果你現在只是想先體驗「把 AI Agent 放進 IDE 裡工作」這件事，Antigravity 是一條很直接的路。

另一個重點是，它不是把你丟到一個純聊天 app 裡，而是保留了 IDE 的工作感：

- 左側還是檔案與工作區。
- 中間還是你熟悉的編輯區。
- 右側則是 Agent 對話與工作面板。

這種排法很重要，因為它讓 AI 不是飄在外面，而是真正留在你的開發現場。

# 4. 這兩種方法怎麼選

如果把 GitHub Copilot Education + VS Code 與 Antigravity 放在一起看，我會這樣理解：

| 方案 | 主要門檻 | 優勢 | 比較適合誰 |
| --- | --- | --- | --- |
| GitHub Copilot Education + VS Code | 需要學生或教師資格，且要先完成 GitHub Education 審核 | 生態成熟、直接整合 GitHub 與 VS Code、可在熟悉環境中協作 | 已經在用 GitHub 與 VS Code，且具備教育身分的人 |
| Antigravity | 只要能登入帳號即可開始，進入成本較低 | 上手快、介面接近 VS Code、能快速體驗 IDE 內 Agent 協作 | 想先用最低成本開始，或沒有 GitHub Education 資格的人 |

如果你本來就是學生，而且平常主要工作環境就是 VS Code，那我會優先推薦 **GitHub Copilot Education**。因為它幾乎是把 AI 直接嵌進你已經在用的開發流程裡。

如果你現在沒有教育資格，或者你只是想先感受一下「在 IDE 中跟 AI Agent 協作」到底有多大差別，那麼 **Antigravity** 會是更快的入口。

# 5. 我最推薦的用法：把 AI 當協作者，不是自動駕駛

這篇文章最重要的，不是介紹哪個工具比較炫，而是提醒一件事：

**最健康的使用方式，仍然是 Human in the loop。**

也就是說，AI 可以讀、可以想、可以提案、可以產生修改，但最後的決策權一定要留在人手上。這樣的工作流我認為最穩：

1. **先叫 AI 讀，不要急著改**  
   先讓它讀相關檔案，說明模組關係、資料流向與可能風險。

2. **先叫 AI 提計畫，再動手**  
   要它先列出會改哪些檔案、準備怎麼改、可能的副作用是什麼。

3. **限制它修改的範圍**  
   例如只准改某兩個檔案，或先只做最小可行修改。

4. **看 diff，再決定要不要接受**  
   這也是 IDE 方案最大的優勢。你不是看一段抽象回答，而是看具體變更。

5. **自己跑測試、自己做最後 commit**  
   AI 可以幫忙，但責任不能外包。

你甚至可以直接用這種 prompt 習慣：

- `先不要改 code，先讀目前 workspace 中與登入流程相關的檔案，整理依賴關係給我。`
- `先提出修改計畫，列出預計變更的檔案與原因。`
- `只修改這兩個檔案，其餘檔案不要動。`
- `修改後請用條列說明每一處變更的理由。`

這種用法的本質不是偷懶，而是把 AI 變成一個**可以被審查的協作者**。

# 6. 哪些情境最適合在 IDE 中使用 AI Agent

我自己覺得，下面幾種情境特別適合：

- **接手陌生專案時**  
  先讓 AI 幫你整理入口點、模組關係與重要依賴。

- **要做小功能或局部重構時**  
  先請它提出改法，再由你決定採哪一版。

- **要補測試時**  
  這類工作常常脈絡清楚、規則固定，很適合交給 AI 先打底。

- **要補文件、註解、README 時**  
  AI 很適合幫忙整理已存在的內容。

- **要找跨檔案 bug 時**  
  當問題橫跨多個模組時，IDE 內的上下文能力會比瀏覽器聊天方便很多。

相反地，如果你完全不看 diff、不做測試、也不確認它的推論是否合理，那再強的 AI Agent 也一樣可能把你帶進坑裡。

# 7. 結語

對我來說，AI 最有價值的位置，不是在瀏覽器裡當一個很會聊天的機器人，也不是在 CLI 裡盲目自動執行所有指令，而是**進到 IDE 裡，成為一個能讀專案、能提出修改、能被你審查的協作者**。

這也是為什麼我會特別推薦這兩種免費做法：

- 有教育資格，就走 **GitHub Copilot Education + VS Code**。
- 想快速開始，就試試 **Antigravity**。

真正值得追求的，不是讓 AI 取代你，而是建立一個更好的協作流程：

- AI 負責讀得快、整理快、產生草稿快。
- 人負責判斷、取捨、驗證與最後決策。

這樣的組合，才比較像真正可持續的開發方式。
