> 本文整理 `vLLM`、`Ollama`、`llama.cpp` 三種常見的 LLM inference 工具，內容以 **2026 年 3 月 24 日** 可查到的官方文件為基準。  
> 先總結一下這三者的定位：**企業高併發服務選 `vLLM`，個人快速上手選 `Ollama`，想把本機、Mac 或低資源設備壓榨到極限就看 `llama.cpp`。**

很多人第一次接觸 LLM inference 工具時，都會把 `vLLM`、`Ollama`、`llama.cpp` 放在一起比較。這很合理，因為三者都能讓模型「跑起來」，也都和本地部署、API、效能優化有關。

但它們其實 **不是同一層級的工具**。

- `vLLM` 比較像面向服務端的高效能推論引擎
- `Ollama` 比較像面向個人開發者的本機模型執行與管理工具
- `llama.cpp` 則更像是底層、輕量、可移植、可深度調校的推論框架

如果不先釐清這個差異，很容易出現兩種誤判：

- 想在公司內部扛高併發 API，卻選了最方便但不一定最適合大規模服務化的工具
- 想在自己的筆電快速試模型，卻一開始就跳進需要大量底層設定的方案

所以這篇文章的重點不是硬要分出誰最強，而是幫你看懂：**三者各自在什麼情境下最合理。**

---

# 1. 為什麼這三個工具常被放在一起比較

在 LLM 的世界裡，訓練（training）和推論（inference）是兩件不同的事。大多數開發者在日常工作中碰到的，不是自己訓練一個新模型，而是把已經存在的模型載入、執行、包成 API，或者讓它在自己的電腦上可用。

`vLLM`、`Ollama`、`llama.cpp` 之所以常被一起提到，就是因為它們都參與了這件事：**把模型有效率地執行起來**。

不過它們的出發點明顯不同：

- `vLLM` 的核心目標是高吞吐量（throughput）與服務化部署
- `Ollama` 的核心目標是降低本地使用門檻
- `llama.cpp` 的核心目標是讓 LLM 能在更多硬體、更少依賴、更低資源的條件下運行

換句話說，這三者不是互相完全取代的關係，而更像是三種不同的工程取向：

- 你在乎很多人同時使用時的效率，就會偏向 `vLLM`
- 你在乎安裝快、用法直覺、API 立即可用，就會偏向 `Ollama`
- 你在乎量化、平台相容性、CPU / Apple Silicon 表現與更高控制力，就會偏向 `llama.cpp`

# 2. vLLM：偏向服務化與高吞吐量的推論引擎

## 2.1 它是什麼

`vLLM` 是由 UC Berkeley 團隊發起、後來持續演化成社群驅動的開源 LLM inference 與 serving 專案。它最常被拿來做的事情，不是「在筆電上方便試模型」，而是 **把模型部署成高效率的推論服務**。

它最知名的技術之一是 `PagedAttention`。直觀地說，`PagedAttention` 的核心概念是把每個請求的 `KV cache` 拆成較小的區塊管理，降低記憶體浪費，讓 GPU 記憶體利用更有效率。搭配 continuous batching，`vLLM` 在多請求並行的情境下，通常會比單純把 Hugging Face Transformers 直接包成服務更有效率。

官方文件也明確把它定位成一個強調：

- 高吞吐量 serving
- `PagedAttention`
- continuous batching
- OpenAI-compatible API server

的推論框架。

## 2.2 核心優勢

`vLLM` 最強的地方，是它從一開始就不是把「本地跑模型」當作唯一目標，而是把「**如何把模型變成可以穩定服務多個請求的系統**」放在核心。

它的主要優勢包括：

- **高吞吐量**：對需要同時處理多個 request 的服務端情境特別有利
- **OpenAI-compatible API server**：很多現有應用只要改 base URL，就能接到 `vLLM` 啟動的服務
- **批次與快取管理做得成熟**：對長上下文、多使用者、持續進來的請求比較友善
- **硬體支援比早期更廣**：實務上最常見於 GPU 服務部署，但官方文件也已支援更多硬體後端與插件生態，不再只是單一 NVIDIA 故事

如果你今天的需求是「要把模型變成公司內部 API」、「要讓多人同時調用」、「要把硬體資源吃得更有效率」，`vLLM` 幾乎就是最先該看的方案之一。

## 2.3 典型使用場景

`vLLM` 特別適合下面幾種情境：

- 企業內部聊天機器人或知識庫 API
- 提供多人同時使用的推論服務
- 想做 OpenAI API 風格相容的內部替代端點
- 需要長上下文、prefix caching、批次請求優化的服務

如果你的使用者不是你自己，而是一群同事、客戶、產品功能，`vLLM` 的價值會快速放大。

## 2.4 主要限制與不適合誰

`vLLM` 的問題不是不好，而是它的最佳解常常出現在「服務端」。

它的主要限制包括：

- **上手門檻比 Ollama 高**：通常需要對 Python、模型服務、部署環境有基本理解
- **官方不原生支援 Windows**：官方文件明確建議 Windows 使用者改走 `WSL` 或社群維護方案，實務上多半仍以 Linux 為主
- **不是為了最懶人本機體驗而設計**：如果你的目標只是在筆電上快速跑一下模型，`vLLM` 往往不是最省事的第一選擇
- **最佳價值通常要在較完整的硬體與部署情境下才能發揮**：特別是多人併發、服務化、GPU 資源管理

所以，`vLLM` 很適合「有部署意圖」的工程場景，但不一定適合剛開始試水溫的人。

---

# 3. Ollama：偏向本機開箱即用的模型管理與執行工具

## 3.1 它是什麼

如果說 `vLLM` 比較像推論服務引擎，那 `Ollama` 就更像是 **本地 LLM 世界的開箱工具箱**。

它最吸引人的地方，不是讓你接觸所有底層細節，而是把很多麻煩事先包起來。你通常只要安裝 `Ollama`，再執行像 `ollama run llama3` 這樣的命令，它就會幫你處理模型下載、啟動、執行與本機 API。

官方文件也很直接把它描述成最容易上手的大模型入口之一，並提供：

- macOS、Windows、Linux 安裝
- 本機 API
- Python / JavaScript 官方函式庫
- 模型庫與快速拉取流程

## 3.2 核心優勢

`Ollama` 最大的價值就是四個字：**先用再說**。

它的優勢主要在：

- **安裝與使用門檻低**：對多數開發者來說，這是最短的起跑線
- **跨平台**：macOS、Windows、Linux 都可直接安裝
- **模型管理直觀**：有點像把模型執行做成類似容器體驗
- **本機 API 內建可用**：跑起來之後很快就能和應用程式串接
- **很適合原型開發**：例如 local chatbot、測試 prompt、做小型桌面或後端應用

很多人第一次做 local AI app，就是因為 `Ollama` 幾分鐘內可以有結果。這種「從零到可用」的距離非常短，對入門者特別重要。

## 3.3 典型使用場景

`Ollama` 很適合：

- 在個人電腦上快速試不同模型
- 開發本地 AI app、桌面工具、個人助理
- 快速接一個本機 API 做 prototype
- 想把模型執行這件事簡化，不想一開始就碰太多底層參數

如果你現在最需要的不是極限性能，而是「今天就先跑起來」，那 `Ollama` 幾乎是最自然的起點。

## 3.4 主要限制與不適合誰

`Ollama` 的代價，就是它為了簡化使用體驗，會幫你隱藏很多底層選項。

這帶來的限制包括：

- **底層控制力不如 llama.cpp 那麼高**
- **在大規模服務化或極致性能調校上，通常不是第一選擇**
- **如果你想非常細緻地控制量化、編譯選項、硬體 backend 或記憶體策略，會覺得被抽象層限制**

所以，`Ollama` 很適合當作本地 LLM 的入口，但不一定是你最後的終點。很多團隊一開始用它做原型，之後才轉向更底層或更偏服務端的方案。

# 4. llama.cpp：偏向輕量、高移植性、量化與本機控制力

## 4.1 它是什麼

`llama.cpp` 是 `ggml-org` 維護的知名開源專案，核心目標很明確：**用盡量少的依賴，讓 LLM 在非常廣泛的硬體上跑起來，而且跑得夠好。**

它最早以純 C/C++ 實作、可在 CPU 上運作、對 Apple Silicon 友善而受到廣泛關注，後來逐漸擴展出更多 backend 與工具鏈。今天談到本地 LLM、量化與 `GGUF`，幾乎不可能不提到 `llama.cpp`。

需要特別強調的是，`llama.cpp` 現在也不只是單純的 CLI 工具。官方 README 已明確提供：

- `llama-cli`
- `llama-server`
- `llama-bench`

等工具，其中 `llama-server` 可以直接提供 **OpenAI-compatible API**。所以如果有人把 `llama.cpp` 理解成「只能命令列互動」，那已經太過時了。

## 4.2 核心優勢

`llama.cpp` 的優勢非常鮮明，而且和 `vLLM`、`Ollama` 幾乎是不同方向：

- **Plain C/C++、依賴少、可移植性高**
- **`GGUF` 生態成熟**：量化模型非常常見，下載與使用流程也更普及
- **量化能力強**：從 1.x-bit 到 8-bit 的整數量化能力，是它極具代表性的優勢之一
- **Apple Silicon 是一等公民**：官方 README 直接強調對 ARM NEON、Accelerate、Metal 的優化
- **CPU 也能用**：即使沒有高階 NVIDIA GPU，仍然能在很多本地設備上跑模型
- **控制力高**：你可以更細緻地決定模型格式、量化等級、硬體使用方式與執行參數

這讓 `llama.cpp` 成為一種很特別的工具：它不是最省事的，但常常是最能讓你「榨出硬體剩餘價值」的方案。

## 4.3 典型使用場景

`llama.cpp` 特別適合：

- MacBook、Mac mini 等 Apple Silicon 裝置上的本地推論
- 沒有高階 GPU，但希望用 CPU 或混合方式跑模型
- 老電腦、迷你主機、邊緣設備、嵌入式設備
- 想要自己掌控模型量化與執行細節
- 想用 `GGUF` 生態來降低模型的記憶體需求

如果你是那種會在意 `Q4`、`Q5`、`Q8` 這類量化版本差異，或者會認真比較「這台 8GB / 16GB 記憶體的機器到底能跑到哪裡」，那你高機率會喜歡 `llama.cpp`。

## 4.4 主要限制與不適合誰

`llama.cpp` 的強，往往和它的門檻綁在一起。

它的主要限制包括：

- **比 Ollama 更底層**：新手第一次碰時，概念負擔通常更高
- **你要自己理解更多東西**：例如模型格式、量化、記憶體、執行參數
- **若只是想快速試模型，不一定比 Ollama 省時間**
- **若你的主要目標是高併發企業 API，通常也不是最先想到的選項**

所以 `llama.cpp` 比較不像「人人都該先用這個」，而更像「當你想更進一步掌握本機 inference 細節時，它會變得非常有吸引力」。

# 5. 快速對比表

| 工具 | 主要對象 | 最佳場景 | 硬體傾向 | 上手難度 | 最大優勢 | 主要代價 |
| --- | --- | --- | --- | --- | --- | --- |
| `vLLM` | 服務端工程師、需要部署推論 API 的團隊 | 企業內部服務、高併發 API、多使用者推論 | 實務上常見於 GPU 服務部署，也支援更多官方硬體後端 | 中 | 吞吐量高、批次處理成熟、OpenAI-compatible server | 對部署環境要求較高，Windows 不原生支援 |
| `Ollama` | 個人開發者、原型開發者 | 本地試模型、快速做 local AI app | CPU / GPU 皆可，跨平台安裝方便 | 低 | 最容易上手、內建本機 API、模型管理直觀 | 底層控制力較低，極致性能調校空間有限 |
| `llama.cpp` | 進階本機玩家、Mac 使用者、邊緣設備開發者 | Apple Silicon、本地量化模型、低資源裝置推論 | CPU、Apple Silicon、也支援多種 GPU backend | 中 | 輕量、相容性高、GGUF 與量化生態成熟 | 需要理解更多底層細節，入門不如 Ollama 輕鬆 |

這張表最重要的訊息不是誰比較厲害，而是：

- `vLLM` 比較偏「服務化效率」
- `Ollama` 比較偏「使用體驗」
- `llama.cpp` 比較偏「控制力與可移植性」

# 6. 我該選哪一個？三種典型場景

## 6.1 公司內部或 API 服務要扛多人併發

如果你的需求是要在公司內部搭一個給很多人用的 AI 服務，或者要把模型包成可以被產品功能呼叫的 API，那最優先該看的通常是 `vLLM`。

原因不是因為它看起來最「工程」，而是它真的把多請求處理、吞吐量、批次與快取管理當成核心問題在解。

**這種情境請優先考慮 `vLLM`。**

## 6.2 筆電上快速試模型或開發本地 AI App

如果你只是想在自己的電腦上快速測試模型、接一個本地 API、做個小型助理或 prototype，那 `Ollama` 往往最合理。

它不一定是最極限的，但通常是最省時間的。對入門者來說，這件事很重要，因為你先得到成果，才有後續優化的意義。

**這種情境請優先考慮 `Ollama`。**

## 6.3 Mac / 舊電腦 / 邊緣設備想壓榨資源效率

如果你是重度 Mac 使用者，或者你手上的設備資源有限，但你願意花一點時間理解量化、模型格式與參數設定，那 `llama.cpp` 的吸引力會非常高。

它讓很多「原本跑不起來」的場景變成「其實可以跑，只是要用對格式與方法」。

**這種情境請優先考慮 `llama.cpp`。**

---

# 7. 結論：沒有最強，只有最適合

`vLLM`、`Ollama`、`llama.cpp` 之所以常被一起比較，不是因為它們完全一樣，而是因為它們剛好分別代表了 LLM inference 的三種典型工程思路：

- 把推論做成高效率服務：`vLLM`
- 把本地使用門檻降到最低：`Ollama`
- 把硬體相容性、量化與控制力做到最大：`llama.cpp`

所以，真正的選法不是問「哪個最強」，而是先問自己：

- 我主要是在做服務，還是在做本機工具？
- 我在乎的是吞吐量，還是上手速度？
- 我需要的是更高抽象層，還是更高控制力？

一旦這三個問題想清楚，你通常就不會再糾結太久。

對大多數剛入門的開發者來說，一個實用的順序往往是：

1. 先用 `Ollama` 了解本地模型與 API 怎麼串
2. 需要更高控制力時深入 `llama.cpp`
3. 進入多人服務與正式部署時評估 `vLLM`

這不是唯一道路，但通常是阻力最小、學習曲線也最自然的一條路。
