> 本文整理 `vLLM`、`Ollama` 與 `llama.cpp` 三種常見的 LLM 推論工具，內容以 **2026 年 3 月 24 日** 可查閱的官方文件為準。
> 三者的定位可以先概括如下：**企業高併發服務可選 `vLLM`，個人快速入門可選 `Ollama`，若希望充分運用本機、Mac 或低資源裝置的硬體效能，則可考慮 `llama.cpp`。**

許多人初次接觸 LLM 推論工具時，會將 `vLLM`、`Ollama` 與 `llama.cpp` 放在一起比較。這樣的比較很合理，因為三者都能執行模型，也都涉及本機部署、API 與效能最佳化。

但它們其實**不是位於同一層次的工具**。

- `vLLM` 是面向伺服器端的高效能推論引擎
- `Ollama` 是面向個人開發者的本機模型執行與管理工具
- `llama.cpp` 則是較底層、輕量、可移植且可深入調校的推論框架

如果未先釐清這項差異，很容易出現兩種錯誤選擇：

- 需要在公司內部提供高併發 API，卻選擇了操作方便但不一定適合大規模服務化的工具
- 只想在筆記型電腦上快速測試模型，卻一開始就採用需要大量底層設定的方案

因此，本文的重點不是勉強比較孰優孰劣，而是說明：**三者各自在何種情境下最為合適。**

---

# 1. 為什麼這三個工具常被放在一起比較

在 LLM 領域中，訓練（training）與推論（inference）是兩項不同的工作。多數開發者日常面對的並非自行訓練新模型，而是載入及執行既有模型、將其封裝成 API，或讓模型能在自己的電腦上使用。

`vLLM`、`Ollama` 與 `llama.cpp` 經常被一併討論，是因為它們都在處理同一項任務：**有效率地執行模型**。

不過它們的出發點明顯不同：

- `vLLM` 的核心目標是高吞吐量（throughput）與服務化部署
- `Ollama` 的核心目標是降低本機使用門檻
- `llama.cpp` 的核心目標是讓 LLM 能在更多硬體平台上，以更少的相依套件及較低資源執行

換句話說，三者並非彼此完全取代，而是代表三種不同的工程取向：

- 重視多人同時使用時的效率，可優先考慮 `vLLM`
- 重視快速安裝、直觀操作與立即可用的 API，可優先考慮 `Ollama`
- 重視量化、平台相容性、CPU／Apple Silicon 效能與更高控制力，可優先考慮 `llama.cpp`

# 2. vLLM：偏向服務化與高吞吐量的推論引擎

## 2.1 它是什麼

`vLLM` 是由 UC Berkeley 團隊發起，後來持續發展為社群驅動的開源 LLM 推論與服務專案。它的主要用途不是在筆記型電腦上方便地測試模型，而是**將模型部署成高效率的推論服務**。

其最知名的技術之一是 `PagedAttention`。簡單來說，`PagedAttention` 會將每個請求的 `KV cache` 拆分成較小區塊加以管理，以減少記憶體浪費並提高 GPU 記憶體利用率。搭配 `continuous batching`（連續批次處理）後，`vLLM` 在多請求並行的情境下，通常比直接將 Hugging Face Transformers 封裝成服務更有效率。

官方文件也明確指出它具備以下特色：

- 高吞吐量推論服務
- `PagedAttention`
- `continuous batching`（連續批次處理）
- OpenAI 相容的 API 伺服器

因此，它是一套以高效能服務為核心的推論框架。

## 2.2 核心優勢

`vLLM` 的主要優勢，在於它從一開始就不只著眼於本機執行模型，而是將「**如何把模型建構成可穩定處理多個請求的系統**」列為核心目標。

它的主要優勢包括：

- **高吞吐量**：特別適合需要同時處理多個請求的伺服器端情境
- **OpenAI 相容的 API 伺服器**：許多既有應用只需修改基礎 URL，即可連接 `vLLM` 啟動的服務
- **成熟的批次與快取管理**：更適合長上下文、多名使用者及持續進入的請求
- **更廣泛的硬體支援**：實務上最常部署於 GPU 伺服器，但官方文件已涵蓋更多硬體後端與外掛生態，不再只限於 NVIDIA 平台

如果需求是將模型建置成公司內部 API、供多人同時呼叫，並提高硬體資源利用率，`vLLM` 通常是最值得優先評估的方案之一。

## 2.3 典型使用場景

`vLLM` 特別適合下面幾種情境：

- 企業內部聊天機器人或知識庫 API
- 提供多人同時使用的推論服務
- 建立與 OpenAI API 介面相容的內部替代端點
- 需要長上下文、prefix caching、批次請求優化的服務

當使用者包含多名同事、客戶或產品功能，而不只是開發者本人時，`vLLM` 的價值會更加明顯。

## 2.4 主要限制與不適用情境

`vLLM` 並非缺乏優勢，只是它最能發揮價值的情境通常位於伺服器端。

它的主要限制包括：

- **入門門檻比 Ollama 高**：通常需要具備 Python、模型服務與部署環境的基本知識
- **官方不原生支援 Windows**：官方文件明確建議 Windows 使用者改走 `WSL` 或社群維護方案，實務上多半仍以 Linux 為主
- **並非以最簡便的本機體驗為設計目標**：如果只想在筆記型電腦上快速執行模型，`vLLM` 往往不是最省時的第一選擇
- **最佳價值通常要在較完整的硬體與部署情境下才能發揮**：特別是多人併發、服務化、GPU 資源管理

因此，`vLLM` 很適合具有明確部署需求的工程情境，但不一定適合初次嘗試 LLM 推論的使用者。

# 3. Ollama：開箱即用的本機模型管理與執行工具

## 3.1 它是什麼

如果說 `vLLM` 是推論服務引擎，那麼 `Ollama` 就像是**本機 LLM 的開箱即用工具箱**。

它的主要特色不是讓使用者接觸所有底層細節，而是預先封裝許多繁複步驟。通常只需安裝 `Ollama`，再執行 `ollama run llama3` 之類的指令，它就會處理模型下載、啟動、執行及本機 API。

官方文件將其定位為容易入門的大型模型工具之一，並提供：

- macOS、Windows、Linux 安裝
- 本機 API
- Python／JavaScript 官方函式庫
- 模型庫與快速拉取流程

## 3.2 核心優勢

`Ollama` 最大的價值在於：**可以迅速開始使用。**

它的優勢主要在：

- **安裝與使用門檻低**：多數開發者都能迅速開始操作
- **跨平台**：macOS、Windows、Linux 都可直接安裝
- **模型管理方式直觀**：提供類似容器的模型執行體驗
- **內建本機 API**：啟動後即可快速與應用程式整合
- **適合原型開發**：例如本機聊天機器人、提示詞測試，以及小型桌面或後端應用程式

許多人首次開發本機 AI 應用程式時選擇 `Ollama`，就是因為它能在幾分鐘內產生結果。這種從安裝到可用的短流程，對初學者格外重要。

## 3.3 典型使用場景

`Ollama` 很適合：

- 在個人電腦上快速試不同模型
- 開發本機 AI 應用程式、桌面工具或個人助理
- 快速連接本機 API 以製作原型
- 簡化模型執行流程，避免一開始就處理過多底層參數

如果目前最重視的不是極致效能，而是立即執行模型，`Ollama` 通常是最自然的起點。

## 3.4 主要限制與不適用情境

`Ollama` 為了簡化使用體驗，會隱藏許多底層選項，這也形成了它的限制。

這帶來的限制包括：

- **底層控制力不如 llama.cpp 那麼高**
- **在大規模服務化或極致效能調校方面，通常不是第一選擇**
- **若要細緻控制量化、編譯選項、硬體後端或記憶體策略，可能會受到抽象層限制**

因此，`Ollama` 很適合作為本機 LLM 的入門工具，但不一定是最終方案。許多團隊先用它製作原型，之後再轉向更底層或更偏向伺服器端的工具。

# 4. llama.cpp：著重輕量、高移植性、量化與本機控制力

## 4.1 它是什麼

`llama.cpp` 是由 `ggml-org` 維護的知名開源專案，核心目標十分明確：**以盡可能少的相依套件，讓 LLM 能在廣泛的硬體平台上有效執行。**

它最初以純 C／C++ 實作、可在 CPU 上執行且對 Apple Silicon 友善等特性受到廣泛關注，後來逐步擴充更多後端與工具鏈。現今談到本機 LLM、量化與 `GGUF`，幾乎都會提及 `llama.cpp`。

需要特別強調的是，`llama.cpp` 現在已不只是單純的 CLI 工具。官方 README 明確列出以下工具：

- `llama-cli`
- `llama-server`
- `llama-bench`

其中，`llama-server` 可以直接提供**與 OpenAI 相容的 API**。因此，將 `llama.cpp` 理解為只能透過命令列互動，已不符合目前的功能範圍。

## 4.2 核心優勢

`llama.cpp` 的優勢十分鮮明，而且與 `vLLM`、`Ollama` 採取的方向明顯不同：

- **使用純 C／C++、相依套件少且可移植性高**
- **`GGUF` 生態成熟**：量化模型非常常見，下載與使用流程也更普及
- **量化能力強**：從 1.x-bit 到 8-bit 的整數量化能力，是它極具代表性的優勢之一
- **完整支援 Apple Silicon**：官方 README 明確強調對 ARM NEON、Accelerate 與 Metal 的最佳化
- **可使用 CPU**：即使沒有高階 NVIDIA GPU，仍能在許多本機裝置上執行模型
- **控制力高**：使用者可以更細緻地決定模型格式、量化等級、硬體使用方式與執行參數

這使 `llama.cpp` 成為一項獨特的工具：它雖不是最簡便的方案，卻經常能更充分地利用既有硬體資源。

## 4.3 典型使用場景

`llama.cpp` 特別適合：

- MacBook、Mac mini 等 Apple Silicon 裝置上的本機推論
- 沒有高階 GPU，但希望使用 CPU 或混合方式執行模型
- 老電腦、迷你主機、邊緣設備、嵌入式設備
- 想要自己掌控模型量化與執行細節
- 想用 `GGUF` 生態來降低模型的記憶體需求

如果使用者重視 `Q4`、`Q5`、`Q8` 等量化版本的差異，或想仔細評估配備 8 GB／16 GB 記憶體的裝置能執行多大的模型，通常會適合使用 `llama.cpp`。

## 4.4 主要限制與不適用情境

`llama.cpp` 的強大功能通常也伴隨較高的使用門檻。

它的主要限制包括：

- **比 Ollama 更接近底層**：初學者首次使用時，通常需要理解更多概念
- **需要自行掌握更多知識**：例如模型格式、量化、記憶體與執行參數
- **若只是想快速試模型，不一定比 Ollama 省時間**
- **若你的主要目標是高併發企業 API，通常也不是最先想到的選項**

因此，`llama.cpp` 並非所有人都應優先使用的工具；當使用者想進一步掌握本機推論細節時，它才會展現更大的吸引力。

# 5. 快速對比表

| 工具 | 主要對象 | 最佳場景 | 硬體傾向 | 上手難度 | 最大優勢 | 主要代價 |
| --- | --- | --- | --- | --- | --- | --- |
| `vLLM` | 伺服器端工程師、需要部署推論 API 的團隊 | 企業內部服務、高併發 API、多使用者推論 | 實務上常部署於 GPU 伺服器，也支援更多官方硬體後端 | 中 | 吞吐量高、批次處理成熟、提供 OpenAI 相容的伺服器 | 對部署環境要求較高，Windows 不受原生支援 |
| `Ollama` | 個人開發者、原型開發者 | 本機測試模型、快速開發本機 AI 應用程式 | CPU／GPU 皆可，且方便跨平台安裝 | 低 | 容易入門、內建本機 API、模型管理直觀 | 底層控制力較低，極致效能調校空間有限 |
| `llama.cpp` | 進階本機使用者、Mac 使用者、邊緣裝置開發者 | Apple Silicon、本機量化模型、低資源裝置推論 | CPU、Apple Silicon，也支援多種 GPU 後端 | 中 | 輕量、相容性高、GGUF 與量化生態成熟 | 需要理解更多底層細節，入門不如 Ollama 容易 |

這張表的重點不是比較孰優孰劣，而是呈現不同定位：

- `vLLM` 比較偏「服務化效率」
- `Ollama` 比較偏「使用體驗」
- `llama.cpp` 比較偏「控制力與可移植性」

# 6. 該選哪一個？三種典型場景

## 6.1 公司內部或 API 服務需要處理多人併發

如果需求是在公司內部建立供多人使用的 AI 服務，或將模型封裝成可由產品功能呼叫的 API，通常應優先評估 `vLLM`。

原因不在於它看起來更具工程導向，而在於它確實以多請求處理、吞吐量、批次與快取管理為核心問題。

**這種情境請優先考慮 `vLLM`。**

## 6.2 在筆記型電腦上快速測試模型或開發本機 AI 應用程式

如果只是想在自己的電腦上快速測試模型、連接本機 API，或製作小型助理與原型，`Ollama` 往往最為合適。

它不一定能提供極致效能，但通常最節省時間。這對初學者十分重要，因為先產生可用成果，後續最佳化才有實際意義。

**這種情境請優先考慮 `Ollama`。**

## 6.3 充分運用 Mac、舊電腦或邊緣裝置的資源

如果是經常使用 Mac 的使用者，或手邊裝置資源有限，但願意花時間理解量化、模型格式與參數設定，`llama.cpp` 會相當具有吸引力。

它能讓許多原本無法執行模型的裝置，透過合適的格式與方法完成推論。

**這種情境請優先考慮 `llama.cpp`。**

---

# 7. 結論：選擇最適合需求的工具

`vLLM`、`Ollama` 與 `llama.cpp` 經常被一起比較，不是因為它們完全相同，而是因為它們分別代表 LLM 推論的三種典型工程思路：

- 把推論做成高效率服務：`vLLM`
- 降低本機使用門檻：`Ollama`
- 把硬體相容性、量化與控制力做到最大：`llama.cpp`

因此，選擇工具時不應只問「哪一個最強」，而要先釐清：

- 我主要是在做服務，還是在做本機工具？
- 我在乎的是吞吐量，還是上手速度？
- 我需要的是更高抽象層，還是更高控制力？

釐清這三個問題後，通常就能迅速縮小選擇範圍。

對多數初學開發者而言，可以採用以下實用順序：

1. 先使用 `Ollama` 了解如何串接本機模型與 API
2. 需要更高控制力時深入 `llama.cpp`
3. 進入多人服務與正式部署時評估 `vLLM`

這並非唯一途徑，但通常較容易入門，學習曲線也較為自然。
