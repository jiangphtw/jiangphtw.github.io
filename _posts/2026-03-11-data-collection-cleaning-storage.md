許多人一提到資料科學，首先想到的是 `Python`、`pandas`、模型，甚至機器學習。
但重新閱讀一份早期的資料科學入門講義後，我更加確定：真正讓專案穩定的，通常不是最後的模型，而是前面的 `資料蒐集`、`資料清理` 與 `資料儲存`。

如果資料來源錯誤、欄位定義不清、時間格式混亂，或資料表無法重複查詢，後續分析再精美，結論也難以成立。
本文將分別說明這三項工作，並涵蓋實務上常見的問題。

---

# 1. 為什麼先講蒐集、清理、儲存

許多入門教材很快就進入如何繪圖或建模，但實際專案更常採用以下順序：

1. 先定義問題。
2. 再蒐集資料。
3. 將資料清理成可供查詢與比較的形式。
4. 放入穩定的儲存結構。
5. 最後進行分析、製作報表與視覺化。

這項順序很重要，因為每個步驟都建立在前一步的成果上。
如果蒐集的資料不正確，再完善的清理也無法補救；如果清理不完整，儲存只會讓混亂長期保留下來。

![資料科學流程中，最常被低估但最影響專案品質的三段工作](/assets/images/260315/data-pipeline-collection-cleaning-storage.svg?v=2)

_圖：分析與視覺化通常是最後呈現的成果，但專案品質往往取決於前面的蒐集、清理與儲存。_

# 2. 資料蒐集並非越多越好

資料蒐集最常見的誤解，是認為先取得所有資料較為保險。
但如果沒有先定義問題，最後通常只會得到大量用途不明、也無法確認能否相互對應的資料。

## 2.1 先回答三個問題

開始蒐集前，至少要先釐清以下三件事：

- 需要回答什麼問題？
- 分析單位是什麼？
- 需要觀察的時間範圍為何？

例如，如果問題是「結帳轉換率為什麼下降」，分析單位可能是 `一次 Session`、`一張訂單` 或 `一位使用者`。
這三種單位會直接影響是否需要蒐集事件紀錄、會員資料與付款失敗紀錄，以及如何串連這些資料。

## 2.2 先區分資料型態

該講義將資料來源分為 `結構化資料`、`半結構化資料` 與 `非結構化資料`，這項分類至今仍然實用。
不同型態的資料，其蒐集方式、清理成本與儲存方法都不相同。

![結構化、半結構化、非結構化資料的差異](/assets/images/260315/data-source-types-structured-semi-unstructured.svg)

_圖：先區分資料型態，才能判斷後續應以資料表、JSON、文件或其他方式處理。_

這三種類型可以理解為：

- `結構化資料`：欄位與格式固定，例如資料庫表格、交易紀錄與試算表。
- `半結構化資料`：具有欄位概念，但各筆資料不一定完整一致，例如 `JSON`、`XML` 與事件 Log。
- `非結構化資料`：沒有固定欄位，例如文章、客服對話、網頁內容、圖片與音訊。

這些差異會直接影響資料的取得方式。
結構化資料通常可以直接透過 `SQL`、表格匯出或 API 取得。
半結構化資料通常需要先展開欄位並處理巢狀結構。
非結構化資料則通常需要先抽取特徵、進行斷詞、OCR 或標註，才能進入後續分析。

## 2.3 蒐集階段應一併記錄的資訊

許多人只取得資料值，卻沒有一併保留上下文，導致後續清理更加困難。

我建議蒐集時至少一併保存：

- `主鍵或識別碼`：例如 `user_id`、`order_id` 或 `session_id`。
- `事件時間`：明確區分發生時間、寫入時間與更新時間。
- `來源資訊`：記錄資料來自哪個系統、API 與版本。
- `欄位定義`：說明每個欄位的意義與單位。
- `原始值`：儘量保留 Raw Data，不要一開始只留下加工後的結果。

以付款狀態為例，如果只保留「成功／失敗」，很可能遺失「銀行拒絕」、「3D 驗證失敗」、「逾時」與「使用者取消」等後續分析所需的資訊。

## 2.4 蒐集階段最常見的錯誤

- 問題尚未定義清楚，就先取得大量資料。
- 缺少主鍵，導致不同來源的資料無法對應。
- 只保留日報表而未保留事件明細，日後無法重新計算。
- 時間欄位未統一時區。
- 資料來源已變更，卻未記錄版本資訊，導致資料定義逐漸漂移。

良好蒐集的重點不在資料量，而在於後續使用者能確認每個欄位的來源、可信程度，以及與其他資料的對應方式。

# 3. 資料清理的本質，是將原始資料轉化為可判讀資料

資料清理不只是讓表格看起來更加整齊。
其真正目的，是將原始資料整理成可查詢、比較與重複處理，而且不同使用者能得到一致結論的資料。

許多專案在這個階段投入最多時間，這也與講義中的提醒一致：大量工作集中於清理資料，而不是模型本身。

![把原始資料問題整理成可分析資料表的清理重點](/assets/images/260315/data-cleaning-checklist.svg)

_圖：資料清理不是單一步驟，而是一系列統一欄位、型別、缺失值、時間與類別定義的工作。_

## 3.1 實際需要進行哪些清理工作

常見的資料清理工作包括：

- `資料篩選`：先排除測試帳號、內部流量與明顯不應納入分析的資料。
- `偵測缺失值`：找出空值、異常值與欄位缺漏。
- `補齊或保留缺失值`：並非所有空值都應補齊，有些應保留為 `NULL`。
- `資料轉換`：例如將字串轉換為數值、布林值或類別欄位。
- `處理時間格式`：統一時區與格式。
- `重塑資料`：將寬表轉換為長表、展開巢狀欄位，或切分、合併欄位。
- `類別標籤整理`：例如判斷 `TW`、`Taiwan` 與 `台灣` 是否應視為同一類。
- `規則化清理`：使用正規表示式或明確規則處理電話、地址、編碼與商品編號。

## 3.2 清理時最重要的是「定義」

真正困難之處通常不在 `pandas` 語法，而在資料定義。

需要先明確定義：

- 空值代表什麼？
- `0` 代表什麼？
- 同一位使用者重複出現時，應以哪一筆為準？
- 訂單建立時間究竟是下單時間，還是付款完成時間？
- 取消、退款與失敗紀錄是否應納入同一張報表？

如果沒有事先記錄這些定義，即使兩位分析師使用同一份資料，也可能得到不同結果。

## 3.3 清理時我最在意的四個原則

### 第一，不要覆蓋原始資料

應保留原始資料，並另外輸出清理後的結果。
只要規則或欄位定義改變，就需要從 Raw Data 重新執行整套流程。

### 第二，清理規則要寫成可重跑的流程

不要讓清理流程只存在於手動操作的 Excel 檔案中。
較穩健的做法，是將每個步驟寫成 `SQL`、`Python` 或 ETL Job，讓其他人與未來的自己都能重新執行。

### 第三，欄位定義要能被別人讀懂

如果清理後只留下：

- `status = 1`
- `type = A`
- `flag = Y`

卻沒有註解或文件，這份資料表很快就會失去可用性。

### 第四，區分「未知」和「沒有」

這點非常重要。
許多錯誤並非源自資料缺失，而是將 `未知`、`不適用` 與 `沒有發生` 混為同一種值。

例如：

- 未填寫生日，不代表可以忽略空字串所代表的狀態。
- 沒有付款紀錄，不等於付款失敗。
- 未出現在某張資料表中，不代表該使用者不存在。

只要這一步判斷錯誤，後續比率、漏斗與分群結果都可能產生偏誤。

# 4. 資料儲存不只是將 CSV 放入資料夾

許多人以為資料儲存只是找一個位置放置檔案。
但從分析角度來看，儲存真正需要解決三項問題：

- 資料能否安全保存？
- 資料能否維持一致？
- 資料能否穩定查詢並重複使用？

這也是關聯式資料庫至今仍然重要的原因。
它不只用於儲存資料，還提供欄位結構、索引、權限、交易一致性與查詢能力。

## 4.1 比起儲存位置，更重要的是資料分層

我會將資料儲存劃分為至少三層：

1. `原始層 Raw`
2. `清理層 Cleaned`
3. `分析層 Mart`

![把原始資料、清理結果與分析資料分層存放的方式](/assets/images/260315/data-storage-raw-cleaned-mart.svg)

_圖：良好的儲存方式不是使用單一資料夾，而是讓 Raw、Cleaned 與 Mart 各自承擔不同責任。_

三個層次的角色各不相同：

- `Raw`：保留原始輸入，不急於解讀，只確保資料可以追溯。
- `Cleaned`：欄位與型別固定、規則明確，可以穩定查詢。
- `Mart`：依分析需求整理的主題資料表，例如每日營收、漏斗轉換率與會員留存。

如果一開始就直接將資料整理成最終報表，短期內雖然快速，但只要需求改變，通常就必須重新處理整套流程。

## 4.2 什麼情況適合關聯式資料庫

具備以下需求時，`RDBMS` 通常仍是首選：

- 欄位結構相對固定。
- 需要執行 `Join`。
- 需要維持交易一致性。
- 具有明確的權限管理需求。
- 報表與查詢會被重複使用。

會員、訂單、付款與商品等資料，很適合存放於關聯式資料庫。

## 4.3 什麼情況才考慮 NoSQL 或文件型儲存

如果資料本身具有以下形式：

- 大量 `JSON`。
- 事件 Log。
- 文件、訊息與快取資料。
- 欄位變動快速，不適合一開始就套用固定 Schema。

NoSQL 或物件儲存可能更加合適。

但必須注意，NoSQL 並不會因為技術較新就必然更好。
它通常用於補充不同使用情境，而不是取代 `SQL`。
如果需求明確需要穩定欄位、關聯查詢與一致性，最終仍會回到關聯式模型。

## 4.4 可用的儲存結構至少應滿足哪些條件

- 具有明確的主鍵。
- 定義欄位型別。
- 提供欄位說明。
- 設定更新頻率。
- 保留版本與來源紀錄。
- 執行資料品質檢查。
- 明確說明資料表的使用對象。

如果無法滿足這些條件，即使資料已經儲存，也很難真正進入可分析狀態。

# 5. 以實際案例串連三項工作

假設目前需要分析電商網站轉換率下降的原因。

可以依照以下方式拆解：

## 5.1 蒐集

首先蒐集：

- 網站流量來源。
- 商品頁瀏覽事件。
- 加入購物車事件。
- 結帳事件。
- 付款失敗紀錄。
- 訂單與會員資料。

## 5.2 清理

接著處理：

- 同一事件是否重複送出。
- 訂單編號格式是否一致。
- 付款狀態值是否統一。
- 時區是否一致。
- 是否應排除測試訂單。
- 漏斗各步驟的定義是否固定。

## 5.3 儲存

最後不應只保留一張報表，而是保留三個層次：

- `raw_events`
- `cleaned_orders`
- `mart_daily_conversion`

如此一來，日後無論要觀察趨勢、比較流量來源與付款方式，或重新計算某一天的轉換率，都能追溯並重新處理資料。

# 6. 結語：資料科學最容易被低估的是中間流程

對剛入門資料科學的讀者，我建議先思考以下問題，而不是急著建立模型：

- 目前究竟需要回答什麼問題？
- 目前的分析單位是什麼？
- 蒐集到的資料能否相互對應？
- 是否已區分空值、未知與未發生？
- 目前的清理流程能否重新執行？
- 儲存的是原始資料、清理後資料，還是分析結果？
- 除了建立者以外，其他人能否理解這份資料表？

資料科學不是從模型開始。
更常見的情況，是先清楚定義問題、正確蒐集資料、妥善完成清理，再將資料存成可重複使用的結構；如此，後續分析與建模才真正具有意義。

**真正能長期支撐決策的，不是某一次華麗的分析，而是前期是否建立了穩固的資料基礎。**
