很多人一提到資料科學，腦中先想到的是 `Python`、`pandas`、模型，甚至是機器學習。
但我重新看了一份早期的資料科學入門講義後，反而更確定一件事：真正把專案做穩的，通常不是最後那段模型，而是前面的 `資料蒐集`、`資料清理`、`資料儲存`。

因為如果資料來源抓錯、欄位定義不清、時間格式混亂、資料表存得無法重複查詢，後面的分析再漂亮，結論也很難站得住腳。
這篇就把這三段拆開來講，而且盡量講到實務上真的會踩的坑。

---

# 1. 為什麼先講蒐集、清理、儲存

很多入門教材會很快進入「怎麼畫圖」或「怎麼建模」，但實際專案更常見的順序其實是：

1. 先定義問題
2. 再蒐集資料
3. 把資料清理成可以被查詢與比較的型態
4. 放進穩定的儲存結構
5. 最後才做分析、報表與視覺化

這個順序很重要，因為後面每一步都在承接前面。
資料沒有收對，清理再努力也救不回來；清理沒有做完整，儲存起來也只是把混亂永久保存下來。

![資料科學流程中，最常被低估但最影響專案品質的三段工作](/assets/images/260315/data-pipeline-collection-cleaning-storage.svg?v=2)

_圖：分析與視覺化通常是最後看見的成果，但專案品質往往先決定在中間的蒐集、清理、儲存。_

# 2. 資料蒐集不是先抓越多越好

資料蒐集最常見的誤解，是以為「先全部抓下來再說」比較保險。
但如果問題沒有先定義，最後通常只會得到一堆不知道怎麼用、也不知道彼此能不能對上的資料。

## 2.1 先回答三個問題

開始蒐集前，至少先把下面三件事講清楚：

- 你要回答的問題是什麼
- 你分析的單位是什麼
- 你需要觀察的時間範圍是什麼

例如，如果問題是「結帳轉換率為什麼下降」，分析單位可能是 `一次 session`、`一張訂單`、或 `一位使用者`。
這三種單位會直接影響你要不要蒐集事件紀錄、會員資料、付款失敗紀錄，以及它們之間怎麼串。

## 2.2 先分清楚資料長什麼樣

那份講義裡把資料來源分成 `結構化資料`、`半結構化資料`、`非結構化資料`，這個分類到現在仍然很好用。
因為不同型態的資料，蒐集方式、清理成本、儲存方式都不一樣。

![結構化、半結構化、非結構化資料的差異](/assets/images/260315/data-source-types-structured-semi-unstructured.svg)

_圖：先分清楚資料型態，後面才知道該用資料表、JSON、文件或其他方式處理。_

這三類可以這樣理解：

- `結構化資料`：欄位固定、格式固定，像資料庫表格、交易紀錄、試算表。
- `半結構化資料`：有欄位概念，但每筆不一定完整一致，像 `JSON`、`XML`、事件 log。
- `非結構化資料`：沒有固定欄位，像文章、客服對話、網頁內容、圖片、音訊。

這個差異會直接影響你怎麼抓資料。
結構化資料通常可以直接用 `SQL`、匯出表格或 API 撈取。
半結構化資料常常要先展開欄位、處理巢狀結構。
非結構化資料則通常要先抽取特徵、做斷詞、OCR、標註，才有機會進入後續分析。

## 2.3 蒐集階段該一起記下來的東西

很多人只抓「值」，卻沒有把「上下文」一起留下來，這會讓後面的資料清理很痛苦。

我會建議蒐集時至少一起保存：

- `主鍵或識別碼`：例如 `user_id`、`order_id`、`session_id`
- `事件時間`：而且要明確是發生時間、寫入時間，還是更新時間
- `來源資訊`：資料來自哪個系統、哪個 API、哪個版本
- `欄位定義`：每個欄位代表什麼，單位是什麼
- `原始值`：能留 raw 就先留 raw，不要一開始就只留加工後的結果

例如付款狀態，如果你只留「成功 / 失敗」，很可能會失去「銀行拒絕」、「3D 驗證失敗」、「逾時」、「使用者取消」這些後續分析很需要的訊息。

## 2.4 蒐集階段最常見的錯誤

- 問題還沒定義清楚，就先抓一大堆資料
- 沒有主鍵，最後無法把不同來源對在一起
- 只留日報表，不留事件明細，之後無法回頭重算
- 時間欄位沒有統一時區
- 來源變更了，但沒有版本資訊，導致資料定義默默漂移

蒐集做得好，重點不是資料量大，而是後面的人知道每一欄從哪裡來、能不能信、怎麼跟別的資料對上。

# 3. 資料清理的本質，是把資料變成可判讀的資料

資料清理不是「讓表格看起來比較整齊」而已。
它真正的目的，是把原始資料整理成一份可以查詢、可以比較、可以重跑，而且不同人看會得到同樣結論的資料。

很多專案花最多時間的就是這裡，這點其實和那份講義的提醒一致：大量時間都花在清理資料，而不是模型本身。

![把原始資料問題整理成可分析資料表的清理重點](/assets/images/260315/data-cleaning-checklist.svg)

_圖：資料清理不是單一步驟，而是一系列把欄位、型別、缺值、時間與類別定義固定下來的工作。_

## 3.1 你實際上會做哪些清理

資料清理常見的工作包含：

- `資料篩選`：先排除測試帳號、內部流量、明顯不該進分析的資料
- `偵測缺失值`：找出空值、異常值、欄位缺漏
- `補齊或保留缺失值`：不是所有空值都要補，有些應該保留為 `NULL`
- `資料轉換`：例如把字串轉成數值、布林值或類別欄位
- `處理時間格式`：統一成同一個時區、同一個格式
- `重塑資料`：寬表轉長表、巢狀欄位展開、欄位切分或合併
- `類別標籤整理`：例如 `TW`、`Taiwan`、`台灣` 要不要視為同一類
- `規則化清理`：用正規表示式或清楚規則處理電話、地址、代碼、商品編號

## 3.2 清理時最重要的是「定義」

真正困難的地方通常不是 `pandas` 語法，而是定義。

你要先定義清楚：

- 空值代表什麼
- `0` 代表什麼
- 同一個使用者重複出現時，哪一筆算準
- 一筆訂單的建立時間，究竟是下單時間還是付款完成時間
- 取消、退款、失敗，要不要算進同一張報表

如果這些定義沒有先寫下來，兩個分析師即使用同一份資料，也可能做出不同的結果。

## 3.3 清理時我最在意的四個原則

### 第一，不要覆蓋原始資料

原始資料要保留，清理過的結果另外輸出。
因為只要規則改了、欄位理解變了，你就需要從 raw 重新跑一遍。

### 第二，清理規則要寫成可重跑的流程

不要把清理流程留在手動操作的 Excel 裡。
比較穩的做法是把每個步驟寫成 `SQL`、`Python`、或 ETL job，讓別人能重跑，你自己下週也能重跑。

### 第三，欄位定義要能被別人讀懂

如果你清理完只留下：

- `status = 1`
- `type = A`
- `flag = Y`

但沒有註解或文件，這份資料表很快就會失去可用性。

### 第四，區分「未知」和「沒有」

這點非常重要。
很多錯誤不是來自資料缺失，而是把 `未知`、`不適用`、`沒有發生` 混成同一種值。

例如：

- 沒填生日，不等於生日是空字串就能忽略
- 沒有付款紀錄，不等於付款失敗
- 沒出現在某張表，不等於這個人不存在

只要這一步判錯，後面的比率、漏斗、分群都可能被帶偏。

# 4. 資料儲存不是把 CSV 放進資料夾就結束

很多人以為資料儲存只是「找個地方放檔案」。
但從分析角度來看，儲存真正要解決的是三件事：

- 資料能不能安全保存
- 資料能不能維持一致
- 資料能不能被穩定查詢與重複使用

這也是為什麼關聯式資料庫到現在仍然很重要。
它不只是存東西而已，而是提供欄位結構、索引、權限、交易一致性、查詢能力。

## 4.1 比起「放哪裡」，更重要的是怎麼分層

我會把資料儲存想成至少三層：

1. `原始層 Raw`
2. `清理層 Cleaned`
3. `分析層 Mart`

![把原始資料、清理結果與分析資料分層存放的方式](/assets/images/260315/data-storage-raw-cleaned-mart.svg)

_圖：好的儲存不是單一資料夾，而是讓 raw、cleaned、mart 各自有不同責任。_

這三層的角色不同：

- `Raw`：保留原始輸入，不急著解讀，只確保可追溯
- `Cleaned`：欄位固定、型別固定、規則明確，可以穩定查詢
- `Mart`：依分析需求整理好的主題資料表，例如每日營收、漏斗轉換率、會員留存

如果你一開始就直接把資料「整理到最終報表」，短期很快，但後面只要需求一改，通常得整條重做。

## 4.2 什麼情況適合關聯式資料庫

當你有這些需求時，`RDBMS` 通常仍然是首選：

- 欄位結構相對固定
- 需要 `join`
- 需要交易一致性
- 有明確權限管理需求
- 報表與查詢會被重複使用

例如會員、訂單、付款、商品這類資料，很適合放在關聯式資料庫。

## 4.3 什麼情況才考慮 NoSQL 或文件型儲存

如果你的資料本來就比較像：

- 大量 `JSON`
- 事件 log
- 文件、訊息、快取資料
- 欄位變動很快，且不適合一開始就硬塞固定 schema

那 NoSQL 或物件儲存會比較順手。

但要注意，NoSQL 不是比較新就一定比較好。
它通常是補不同場景，而不是取代 `SQL`。
如果你的問題明明需要穩定欄位、關聯查詢與一致性，最後還是會回到關聯式模型。

## 4.4 一份可用的儲存結構，至少該滿足這些事

- 有清楚的主鍵
- 有欄位型別
- 有欄位說明
- 有刷新頻率
- 有版本與來源紀錄
- 有資料品質檢查
- 有人知道這張表是給誰用的

如果做不到這些，資料就算存下來，也很難真正進入「可分析」狀態。

# 5. 用一個實際例子把三段串起來

假設你今天要分析電商網站的轉換率下降。

那你可以這樣拆：

## 5.1 蒐集

你先抓：

- 網站流量來源
- 商品頁瀏覽事件
- 加入購物車事件
- 結帳事件
- 付款失敗紀錄
- 訂單與會員資料

## 5.2 清理

你接著要處理：

- 同一事件是否重複送出
- 訂單編號格式是否一致
- 付款狀態值是否統一
- 時區是否一致
- 測試訂單要不要排除
- 漏斗每一步的定義是否固定

## 5.3 儲存

最後你不會只留一張報表。
你通常會留三層：

- `raw_events`
- `cleaned_orders`
- `mart_daily_conversion`

這樣之後無論要看趨勢、分來源比較、付款方式差異，還是重算某一天的轉換率，都有回頭的空間。

# 6. 寫在最後：資料科學最容易被低估的，其實是中間這段

如果你是剛入門資料科學，我會很建議先把注意力放在下面這幾題，而不是急著跳模型：

- 我現在到底要回答什麼問題
- 我現在分析的單位是什麼
- 我蒐集到的資料能不能互相對上
- 空值、未知、沒有發生，三者有沒有分清楚
- 我現在的清理流程能不能重跑
- 我存下來的是原始資料、清理資料，還是分析結果
- 這份資料表除了我自己，別人能不能看懂

資料科學不是從模型開始。
更常見的情況是，你先把問題講清楚，把資料蒐集對，把資料清理乾淨，把資料存成可重複使用的結構，後面的分析與建模才真的有意義。

**真正能長期支撐決策的，不是某一次很炫的分析，而是你有沒有把前面的資料基礎打穩。**
