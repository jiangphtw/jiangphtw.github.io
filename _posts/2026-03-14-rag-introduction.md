許多人第一次接觸 `RAG` 時，直覺上會將它理解為：
「將文件提供給模型，模型的回答就會更加準確。」

這種說法不能算錯，卻過度簡化了整套架構。
`RAG` 真正重要的地方，不在於是否將文件放入上下文，而是有沒有在模型回答前，將 `尋找資料` 設計成一套獨立流程。

換句話說，`RAG` 的核心不是特殊的 Prompt，而是以下順序：

1. 先理解使用者的問題。
2. 再到外部知識庫尋找相關內容。
3. 將找到的內容與問題一併交給模型。
4. 最後生成答案。

本文暫不深入實作細節，而是先整理 `RAG` 的基本概念、流程、優點、限制與常見誤解。
日後可再另行撰寫偏重實作的版本。

---

# 1. 為什麼會需要 RAG

首先從最根本的問題開始。

大型語言模型擅長：

- 理解語言
- 生成語言
- 根據訓練資料的分布組織合理答案

但模型不一定知道：

- 公司內部文件的最新版本。
- 某項產品的價格是否在上週變更。
- 某份規格書第 17 頁的內容。
- 某項客服政策是否在昨天更新。

換句話說，`LLM` 雖然強大，本身卻不是即時知識庫。

如果只依賴模型內部的知識，很快就會遇到幾項問題：

- 知識可能過時。
- 模型不具備組織內部的私有資料。
- 答案看似合理，實際上卻不是依據指定來源生成。

![為什麼需要在生成前先檢索資料](/assets/images/260315/rag-why-retrieval-matters.svg)

_圖：`RAG` 不是替代模型，而是在模型回答前先補充外部知識。_

這也是 `RAG` 最直接的價值：

**讓模型不只依賴內部知識，而能先參考外部資料再回答。**

---

# 2. RAG 是什麼

`RAG` 是 `Retrieval-Augmented Generation` 的縮寫。
這個名稱已清楚表達整套流程：

- `Retrieval`：先檢索資料。
- `Augmented`：將資料加入上下文。
- `Generation`：再生成答案。

因此，它不是單一模型或資料庫，而是一種系統架構。

可以將它理解為：

- 模型負責理解問題並組織答案。
- 檢索系統負責尋找有用的外部資訊。

兩個部分結合後，才形成完整的 `RAG`。

---

# 3. 最基本的 RAG 流程

最基本的 `RAG` 流程大致包含以下步驟：

1. 準備文件。
2. 切分 Chunk。
3. 轉換成 Embedding。
4. 存入索引或向量資料庫。
5. 接收使用者問題。
6. 將問題轉換為檢索查詢。
7. 找回最相關的 Chunk。
8. 將 Chunk 與問題一併交給模型。
9. 生成答案。

![RAG 的基本流程](/assets/images/260315/rag-pipeline-overview.svg)

_圖：`RAG` 的重點不只有最後的 LLM，也包括前面的文件整理與檢索流程。_

這裡要特別注意一件事：

許多人以為 `RAG` 的核心在最後一段 Prompt。
但在實務上，前面的幾個步驟往往更能決定最終效果：

- 文件切分是否合適？
- Embedding 品質是否良好？
- 檢索內容是否準確？
- Metadata Filter（中繼資料篩選）是否設計清楚？

如果檢索內容一開始就不正確，後續模型再強大，也只會更流暢地表達錯誤上下文。

# 4. RAG 各階段的作用

## 4.1 文件準備

首先需要準備資料來源。

常見來源可能是：

- PDF
- FAQ
- Wiki
- 規格文件
- API 文件
- 客服知識庫
- 合約與內部政策

這一步看似簡單，實際上卻十分重要。
如果資料來源本身混亂、版本不明且高度重複，後續檢索品質通常不會理想。

## 4.2 Chunking

模型不會直接讀取整個資料庫，通常需要先將文件切成較小片段，也就是 `Chunk`。

這一步的核心問題是：

- 每個片段應切多大？
- 是否需要 Overlap（重疊）？
- 應依段落、標題，還是固定字數切分？

切分得太小，語意可能不完整。
切分得太大，檢索時則容易一併帶回許多無關資訊。

因此，`Chunking` 不只是技術細節，也是影響 `RAG` 品質的關鍵環節之一。

## 4.3 Embedding

接著，通常會將每個 Chunk 轉換成向量表示，也就是 `Embedding`。

這樣做的目的，是讓系統不只依賴關鍵字，也能根據語義相似度尋找資料。

例如使用者問：

「可以退費嗎？」

系統不一定要只找出文字完全包含「退費」的段落，也可能找出包含：

- 退款
- cancellation
- refund policy

這就是 Embedding 在 `RAG` 中的價值。

## 4.4 Retrieval

這一步是在回答：

「在大量 Chunk 中，哪些片段最值得優先取回？」

常見做法可能包含：

- 向量相似度搜尋
- keyword search
- hybrid search
- metadata filter
- reranking

換句話說，`Retrieval` 不一定只有一種方式。
成熟的系統往往會結合多種檢索策略。

## 4.5 Generation

最後，將以下內容：

- 使用者問題
- 檢索回來的內容
- 系統規則

一併交給 `LLM` 生成答案。

這一步通常還會加入幾項要求：

- 只能根據提供的資料回答。
- 找不到資料時，必須明確說明無法回答。
- 附上引用段落或來源。

這些要求都是為了降低模型任意延伸內容的空間。

# 5. RAG 改善了哪些問題

`RAG` 的主要價值不是讓模型突然變得更聰明，而是提高整套系統的可控性。

## 5.1 讓答案可以連回資料來源

這點非常重要。

如果模型直接回答，很難得知內容依據哪項來源。
但 `RAG` 可以將回答與來源段落連結在一起。

這就代表：

- 更容易驗證。
- 更容易除錯。
- 更容易取得使用者信任。

## 5.2 讓系統可以用最新資料

模型本身的訓練資料通常不是即時更新的。
但 `RAG` 可以透過外部知識庫處理更新。

換句話說，文件更新時不一定要重新訓練模型，只需要：

- 更新資料
- 重建索引
- 重做 embedding

系統便有機會根據新內容回答。

## 5.3 讓私有資料能被模型利用

許多企業建置問答系統時，真正需要查詢的不是公開知識，而是：

- 內部 SOP
- 產品規格
- 客服政策
- 合約內容
- 專案文件

這些資料通常不在模型的公開訓練資料中。
`RAG` 正是用來補足這項缺口。

![RAG 改善了什麼，又沒有改善什麼](/assets/images/260315/rag-benefits-and-limits.svg)

_圖：`RAG` 能補最新知識、私有知識與可追溯性，但不會自動解決所有回答品質問題。_

# 6. RAG 無法解決哪些問題

這一點也必須說明清楚，否則容易對 `RAG` 產生錯誤期待。

## 6.1 無法找到正確資料時，答案仍會有問題

如果 retrieval 本身失敗了，例如：

- chunk 切得太碎
- embedding 不適合
- query 沒改寫好
- filter 條件錯了

生成階段取得的上下文本身就不正確，最終答案自然不會可靠。

## 6.2 取回更多資料不一定更好

許多人一開始會直覺地想：

「提供更多資料給模型，不就能改善結果嗎？」

但這通常會產生另一個問題：

- 資訊噪音增加。
- 相關內容被稀釋。
- 模型更難掌握真正重點。

因此，`RAG` 的目標不是找得越多越好，而是取回最相關的少數片段。

## 6.3 模型仍可能產生錯誤摘要

即使來源是對的，模型還是可能：

- 摘錄錯誤重點。
- 錯誤合併不同內容。
- 過度延伸來源資訊。
- 將條件誤述為結論。

因此，`RAG` 能降低幻覺，卻無法完全消除幻覺。

## 6.4 RAG 無法補救低品質文件

如果知識庫本身就是：

- 過期
- 矛盾
- 重複
- 無版本
- 沒結構

系統只會更穩定地取回低品質資料。

因此，許多 `RAG` 專案最後遇到瓶頸時，問題往往不在 LLM，而在文件治理。

---

# 7. 什麼情況下適合做 RAG

`RAG` 很適合以下情境：

- 文件問答
- FAQ 助理
- 企業內部知識搜尋
- 客服輔助回答
- 規格書 / 法規 / 合約檢索
- 開發文件助理
- 附帶來源引用的 RAG 對話系統

這些場景的共同點是：

- 問題需要依賴外部文件
- 文件會更新
- 回答最好能附來源
- 單靠模型記憶不夠可靠

---

# 8. 什麼情況下不一定要用 RAG

不是所有 AI 問答都需要 `RAG`。

如果你的問題比較像：

- 純文案生成
- 摘要你剛貼進來的一小段文字
- 一般公開知識問答
- 不需要依賴特定私有資料

在這些情況下，直接使用模型可能已經足夠。

換句話說，`RAG` 真正適合的是：

**答案必須明確依賴某個外部知識來源的場景。**

如果答案原本就不需要依據特定資料，強行加入 `RAG` 有時只會增加系統複雜度。

# 9. 初學者最常見的 RAG 誤解

以下整理幾個常見誤解。

## 9.1 「有向量資料庫就等於有 RAG」

不是。

向量資料庫只是其中一段基礎設施。
完整的 `RAG` 還包含：

- 文件前處理
- chunking
- embedding
- query 處理
- retrieval
- prompt 組裝
- answer generation

## 9.2 「RAG 就是不斷加入更多文件」

不是。

文件變多只會讓系統更需要：

- 好的索引
- 好的 filter
- 好的 reranking
- 好的文件治理

## 9.3 「RAG 表現不佳，就是模型不夠強」

很多時候不是。

更常見的是：

- 文件切法有問題
- 檢索策略有問題
- 來源資料本身有問題
- Query 與 Chunk 根本不在同一個語義空間中

因此，`RAG` 的效果通常無法只根據模型判斷。

---

# 10. 結語：RAG 是系統工程，而不只是 Prompt 技巧

最值得記住的一句話是：

**`RAG` 的核心不是讓模型記住更多內容，而是讓模型在回答前先查詢資料。**

因此，`RAG` 的品質往往不只取決於模型，也取決於整套系統：

- 文件是否乾淨且一致？
- Chunk 切分是否合適？
- Embedding 與 Retrieval 是否對齊？
- Prompt 是否正確使用上下文？
- 回答能否追溯至來源？

因此，如果日後想進一步建置 `RAG`，較好的順序不是一開始就堆疊大量框架，而是先理解上述問題。
