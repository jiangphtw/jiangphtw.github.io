很多人第一次接觸 `RAG` 時，直覺會把它理解成：
「把文件丟給模型，然後模型就會比較準。」

這樣講不能算錯，但也太粗了。
因為 `RAG` 真正重要的地方，不是「有沒有把文件放進去」，而是你有沒有把 `找資料` 這件事，從模型回答之前就先拆成一條獨立流程。

也就是說，`RAG` 的核心不是神奇 prompt，而是這個順序：

1. 先理解使用者問了什麼
2. 再去外部知識庫找相關內容
3. 把找到的內容連同問題一起交給模型
4. 最後才生成答案

這篇先不進實戰細節，而是把 `RAG` 的基本概念、流程、優點、限制和常見誤解整理清楚。
之後如果有空，再另外寫一篇偏實作的版本。

---

# 1. 為什麼會需要 RAG

先從最根本的問題開始。

大型語言模型很會做的，是：

- 理解語言
- 生成語言
- 根據訓練過的分布，組織出合理答案

但它不一定知道：

- 你公司內部文件最新版本是什麼
- 某個產品的價格是不是上週才改過
- 某份規格書第 17 頁怎麼寫
- 某個客服政策是不是昨天才更新

也就是說，`LLM` 很強，但它本身不是你的即時知識庫。

如果你只靠模型本身記得的知識，很快就會遇到幾個問題：

- 知識過時
- 沒有你的私有資料
- 答案看起來合理，但其實不是根據你要的來源來回答

![為什麼需要在生成前先檢索資料](/assets/images/260315/rag-why-retrieval-matters.svg)

_圖：`RAG` 不是在替代模型，而是在模型回答前，先把外部知識補進來。_

這也是 `RAG` 最直白的價值：

**讓模型不要只靠記憶回答，而是先根據外部資料再回答。**

---

# 2. RAG 到底是什麼

`RAG` 是 `Retrieval-Augmented Generation` 的縮寫。
字面上其實就已經把整件事講得很清楚：

- `Retrieval`：先檢索資料
- `Augmented`：把資料補進上下文
- `Generation`：再生成答案

所以它不是單一模型，也不是單一資料庫，而是一種系統架構。

你可以把它想成：

- 模型負責「理解問題和組織答案」
- 檢索系統負責「找到有用的外部資訊」

這兩段合起來，才是完整的 `RAG`。

---

# 3. 一個最基本的 RAG 流程長什麼樣

如果先講最陽春的版本，一套 `RAG` 流程大致有這幾段：

1. 文件準備
2. 切 chunk
3. 轉 embedding
4. 存進索引或向量資料庫
5. 使用者提問
6. 把問題轉成檢索查詢
7. 找回最相關的 chunk
8. 把 chunk 和問題一起餵給模型
9. 生成答案

![RAG 的基本流程](/assets/images/260315/rag-pipeline-overview.svg)

_圖：`RAG` 的重點不是只有最後一個 LLM，而是前面整條文件整理與檢索流程。_

這裡要特別注意一件事：

很多人以為 `RAG` 的核心在最後一段 prompt。
但實務上，真正最常決定效果的是前面幾段：

- 文件切得好不好
- embedding 好不好
- 檢索回來的內容準不準
- metadata filter 有沒有設計清楚

如果前面找回來的內容就不對，後面模型再強，也只是把錯的上下文講得更漂亮。

---

# 4. RAG 的每一段到底在做什麼

## 4.1 文件準備

你先要有資料來源。

常見來源可能是：

- PDF
- FAQ
- Wiki
- 規格文件
- API 文件
- 客服知識庫
- 合約與內部政策

這一步看起來簡單，但實際上很重要。
因為如果來源本身就混亂、版本不清、重複很多，後面的檢索品質通常不會好。

## 4.2 Chunking

模型不是直接把整個資料庫吞進去，而是通常要先把文件切成較小片段，也就是 `chunk`。

這一步的核心問題是：

- 一段要切多大
- 要不要 overlap
- 要照段落切、標題切，還是固定字數切

切太小，語意可能不完整。  
切太大，檢索時又容易把很多無關資訊一起帶回來。

所以 `chunking` 不是單純技術細節，而是 `RAG` 最常影響品質的環節之一。

## 4.3 Embedding

接著你通常會把每個 chunk 轉成向量表示，也就是 `embedding`。

這樣做的目的，是讓系統可以不是只靠關鍵字，而是用「語意相近」的方式找資料。

例如使用者問：

「可以退費嗎？」

系統不一定要只找出文字完全包含「退費」的段落，也可能找出包含：

- 退款
- cancellation
- refund policy

這就是 embedding 在 `RAG` 裡的價值。

## 4.4 Retrieval

這一步是在回答：

「在一堆 chunk 裡，哪幾段最值得先拿回來？」

常見做法可能包含：

- 向量相似度搜尋
- keyword search
- hybrid search
- metadata filter
- reranking

也就是說，`retrieval` 不一定只有一種方式。
真正成熟的系統，往往是多種檢索策略一起工作。

## 4.5 Generation

最後才是把：

- 使用者問題
- 檢索回來的內容
- 系統規則

一起交給 `LLM`，讓它生成答案。

這一步通常還會再加幾個要求：

- 只能根據提供資料回答
- 沒找到資料就明確說不知道
- 附上引用段落或來源

這些都是為了降低模型自由發揮的空間。

# 5. RAG 真的改善了什麼

`RAG` 最有用的，不是讓模型突然變聰明，而是讓整個系統更可控。

## 5.1 讓答案可以連回資料來源

這點非常重要。

如果模型只是直接回答，你很難知道它是根據哪裡講出這段話。
但 `RAG` 可以讓你把回答和來源段落綁在一起。

這就代表：

- 比較容易驗證
- 比較容易除錯
- 比較容易讓使用者信任

## 5.2 讓系統可以用最新資料

模型本身的訓練資料通常不是即時更新的。
但 `RAG` 可以把更新這件事放在外部知識庫。

也就是說，當文件更新時，你不一定要重訓模型，只要：

- 更新資料
- 重建索引
- 重做 embedding

就有機會讓系統回答新的內容。

## 5.3 讓私有資料能被模型利用

很多企業想做問答系統，真正要問的不是公開知識，而是：

- 內部 SOP
- 產品規格
- 客服政策
- 合約內容
- 專案文件

這些東西本來就不會在模型的公開訓練資料裡。
`RAG` 正是在補這個缺口。

![RAG 改善了什麼，又沒有改善什麼](/assets/images/260315/rag-benefits-and-limits.svg)

_圖：`RAG` 能補最新知識、私有知識與可追溯性，但不會自動解決所有回答品質問題。_

---

# 6. RAG 沒有解決什麼

這點也要講清楚，不然很容易對 `RAG` 抱錯期待。

## 6.1 找不到對的資料時，答案還是會有問題

如果 retrieval 本身失敗了，例如：

- chunk 切得太碎
- embedding 不適合
- query 沒改寫好
- filter 條件錯了

那生成階段拿到的上下文本來就錯，最後答案當然也不會穩。

## 6.2 找回來的資料太多，不代表更好

很多人一開始會直覺想：

「那我多塞一點資料給模型不就好了？」

但這通常會產生另一個問題：

- 資訊噪音變多
- 相關內容被稀釋
- 模型更難抓到真正重點

所以 `RAG` 不是「找到越多越好」，而是「找到最相關的那幾段最好」。

## 6.3 模型還是可能亂總結

即使來源是對的，模型還是可能：

- 摘錯重點
- 合併錯誤
- 過度延伸
- 把條件講成結論

所以 `RAG` 能降低幻覺，但不等於完全沒有幻覺。

## 6.4 文件品質差，RAG 也救不了

如果知識庫本身就是：

- 過期
- 矛盾
- 重複
- 無版本
- 沒結構

那系統只會更穩定地把壞資料找回來。

所以很多 `RAG` 專案最後卡住，問題其實不是 LLM，而是文件治理。

---

# 7. 什麼情況下適合做 RAG

`RAG` 很適合下面這些場景：

- 文件問答
- FAQ 助理
- 企業內部知識搜尋
- 客服輔助回答
- 規格書 / 法規 / 合約檢索
- 開發文件助理
- RAG based chat with source citation

這些場景的共同點是：

- 問題需要依賴外部文件
- 文件會更新
- 回答最好能附來源
- 單靠模型記憶不夠可靠

---

# 8. 什麼情況下不一定要用 RAG

不是所有 AI 問答都需要 `RAG`。

如果你的問題比較像：

- 純文案生成
- 摘要你剛貼進來的一小段文字
- 一般公開知識問答
- 不需要依賴特定私有資料

那直接用模型可能就夠了。

也就是說，`RAG` 真正適合的是：

**答案必須明確依賴某個外部知識來源的場景。**

如果答案本來就不需要回到特定資料，硬上 `RAG` 有時只會讓系統更複雜。

---

# 9. 初學者最常見的 RAG 誤解

這裡我想特別整理幾個很常見的誤解。

## 9.1 「有向量資料庫就等於有 RAG」

不是。

向量資料庫只是其中一段基礎設施。
完整的 `RAG` 還包含：

- 文件前處理
- chunking
- embedding
- query 處理
- retrieval
- prompt 組裝
- answer generation

## 9.2 「RAG 就是不斷塞更多文件」

不是。

文件變多只會讓系統更需要：

- 好的索引
- 好的 filter
- 好的 reranking
- 好的文件治理

## 9.3 「RAG 做起來差，就是模型不夠強」

很多時候不是。

更常見的是：

- 文件切法有問題
- 檢索策略有問題
- 來源資料本身有問題
- 你根本沒有把 query 和 chunk 做在同一種語義空間

所以 `RAG` 的效果，通常不是單看模型就能判斷。

---

# 10. 寫在最後：RAG 比較像一個系統工程，而不是一個 prompt 技巧

我覺得最值得記住的一句話是：

**`RAG` 的核心不是叫模型記住更多，而是讓模型在回答前，先有機會查資料。**

這也是為什麼 `RAG` 做得好不好，往往不只取決於模型，而是取決於整條系統：

- 文件乾不乾淨
- chunk 切得好不好
- embedding 與 retrieval 有沒有對齊
- prompt 有沒有把上下文用對
- 回答能不能回到來源

所以如果你之後想進一步做 `RAG`，更好的順序通常不是一開始就堆很多框架，而是先把這幾件事理解清楚。

之後如果有空，我再接著寫一篇偏實作的版本，把：

- 文件切 chunk
- embedding 建立
- 向量搜尋
- prompt 組裝
- answer with citation

這些部分拆成可操作的流程。
