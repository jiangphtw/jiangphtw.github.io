很多專案一開始以為是標準二元分類 (pass=1 / fail=0)，做到一半才發現：資料裡根本沒有「真實負例」，只有「確定正例」與「其餘未知」。這種設定就是 **PU Learning (Positive-Unlabeled Learning)**。

這篇文章會先用白話說清楚 PU Learning 是什麼、為什麼它很常見，並舉幾個你可能遇過的例子；最後再用我在「認證資料」分析時踩到的坑，示範怎麼把 PU 思維用在真實世界的資料上。

---

# 1. 什麼是 PU Learning

PU Learning 的核心是：你的資料只有兩種狀態。

- `P`：確定為正例 (positive)，例如「確定通過某項認證」、「確定是詐騙」
- `U`：未標註 (unlabeled)，例如「尚未被標註是否通過」、「尚未被確認是否詐騙」

`U` 不是負例，它通常混著兩種東西：

- 真正的正例：其實是正例，但沒有被標註出來
- 真正的負例：確實是負例

因此 PU Learning 和一般監督式二元分類最大的差異是：

- 監督式：你同時擁有「正例」與「真實負例」
- PU：你只有「正例」與「未知」

這差異看起來只是標籤不一樣，但後果很大：如果你把 `U` 直接當負例去訓練，就等同在資料裡塞進大量「假陰性」(false negatives)，模型會被迫學到偏掉的規則，連機率輸出也會失真。

![監督式二元分類 vs PU Learning 示意圖](/assets/images/260305/pu-supervised-vs-pu.svg)

_圖：PU 的關鍵是 `U` 不是「0」，而是一包「未知」，裡面混著正例與負例。_

# 2. PU Learning 的典型例子 (為什麼它很常見)

PU 之所以常見，是因為 **正例通常比較容易被「確認」，負例往往只是「沒被確認」**。

幾個你可能一看就懂的例子：

- 反詐騙：`P`=已確認的詐騙交易；`U`=其他交易 (多數不是詐騙，但也可能漏抓)
- 疾病篩檢：`P`=已確診的人；`U`=沒去檢查或尚未確診的人 (不代表健康)
- 推薦/偏好：`P`=按讚/收藏/購買；`U`=沒互動內容 (可能沒看到，也可能不喜歡)

這些問題如果硬把 `U` 全部當負例 (`0`) 去訓練，常見後果包含：

- 模型把「沒被標註」誤當成「負例特徵」，決策邊界偏掉
- 機率輸出變得不可靠 (不能直接當成真實的 `P(y=1|x)`)
- 指標看起來不錯，但實務決策很容易踩雷

# 3. 一個很常見的「認證資料」陷阱：只有通過紀錄，沒有不通過

接下來進入我實際遇到的案例，但我先把背景說清楚，避免你看到一堆名詞卻不知道在做什麼。

以 NSF 這類第三方認證資料為例，你常看到的是「哪些產品通過了哪些項目」的清單，但不一定看得到「哪些產品沒通過哪些項目」。

我當時手上有一份整理過的資料，內容像是：

- 某些產品，對某些「認證項目」有「通過」的公開紀錄
- 但對於「沒有出現通過紀錄」的項目，我們其實不知道原因

重點在這句：**沒有通過紀錄，不等於不通過。**

![只有通過紀錄的認證資料：空白通常代表未知，不等於不通過](/assets/images/260305/cert-records-unknown-not-fail.svg)

_圖：如果資料來源只記「通過」，那空白格多半是未知 (U)，不要直接當成不通過 (N)。_

它可能代表：

- 產品根本沒有申請那一項
- 有送件，但結果不是通過
- 有通過，但資料沒有收錄到 (例如來源缺漏、更新不同步)
- 或資料整理過程遺漏

換句話說，在這種資料裡：

- `P` = 「確定有通過紀錄」(正例)
- `U` = 「其餘都不知道」(未標註)

這就是很典型的 PU Learning。

---

# 4. 為什麼「把缺的都當不通過」會害你越做越怪

很多人第一個直覺是：沒有通過紀錄就當作 fail=0，然後用一般二元分類硬幹。

這個做法的問題不是「不精準」而已，而是 **標籤語意從一開始就錯了**。你把「未知」當成「不通過」，就等於用錯誤的答案去教模型：

- 你其實在教模型判斷「有沒有被記錄到」，而不是「有沒有通過」
- 你會製造大量假陰性，讓模型學到偏差規則
- 你的評估指標也會很容易被騙：因為 `U` 通常遠多於 `P`，模型只要偏向預測 0，就能拿到看似不錯的 accuracy

到這裡，你會發現：這不是「調整 0 或 0.5 權重」能救的問題，而是要承認資料本質是 PU。

# 5. 面對 PU 資料，你有哪些選項

這裡我用科普角度，把常見做法整理成三類，讓你能快速對照自己的情境。

## 選項 A：重新定義問題 (不假裝有負例)

把任務從「通過/不通過」改成更符合資料事實的目標，例如：

- 「是否有通過紀錄」(recorded vs not recorded)

優點：

- 標籤語意正確，因為我們真的只知道「有紀錄」這件事

缺點：

- 這不等於 pass/fail
- 對外溝通要很小心：你只能說「比較像有紀錄的產品」，不能直接說「一定通過」

## 選項 B：補齊真正的負例 (最根本，但最貴)

如果你能拿到每個產品對每個項目的真實結果：

- pass=1
- fail=0

那就可以回到一般監督式分類，評估也會變得扎實。

但現實是：這通常意味著外部資料、人工補標註、或實驗/送驗成本。

## 選項 C：用 PU Learning 方法 (在只有正例的前提下先做出可用模型)

PU 方法很多，我這裡只講一個最容易理解、也很常被拿來當 baseline 的做法：**PU Bagging**。

---

# 6. 我最後採用的做法：PU Bagging (並把不確定性一起算出來)

PU Bagging 的直覺是：既然 `U` 裡面混著正例與負例，那我們不要一次把整包 `U` 當負例；改成「多次抽樣、多次訓練、最後做平均」。

做法概念如下：

1. 每次訓練都保留所有正例 `P`
2. 從 `U` 隨機抽一小部分，暫時當作偽負例 (pseudo-negative) 來訓練
3. 重複很多次，得到很多個模型的預測
4. 把這些預測取平均，當作最終分數；同時看它們的分散程度，當作「不確定性」

你可以把它想成：「同一題不確定的考題，請很多個同學用不同的假設作答；最後不只看平均答案，也看大家分歧有多大」。

在我這個情境裡，最後會得到兩個很實用的輸出：

- `p_mean`：平均分數。可理解成「有多像正例」或「像通過紀錄的程度」
- `p_std`：分散程度。可理解成「不確定性」或「這個分數有多不穩」

![PU Bagging：多次抽樣訓練，取平均分數並用標準差表示不確定性](/assets/images/260305/pu-bagging-mean-std.svg)

_圖：Bagging 的直覺是「多做幾次不同抽樣的訓練」，平均當分數，分散度當不確定性。_

---

# 7. 結果要怎麼解讀 (以及限制)

## 7.1 最重要的一句話：這不是在學「不通過」

因為我們一開始就沒有真實負例，所以 `p_mean` 不能被解讀成「通過機率」；它比較像：

- 「像不像已知通過紀錄的產品」的分數

如果你把它拿去直接宣稱「一定通過/一定不通過」，就會踩到資料語意的地雷。

## 7.2 把不確定性 (`p_std`) 用進決策，會比硬切 0/1 安全很多

一個實務上好用的解讀方式：

- `p_mean` 高、`p_std` 低：偏向正例，而且判斷穩
- `p_mean` 高、`p_std` 高：看起來像正例，但不確定，建議送驗/人工確認
- `p_mean` 低、`p_std` 低：偏向非正例，而且判斷穩

## 7.3 評估方式也要跟著換

在缺乏真實負例的情況下，硬做 accuracy/F1 容易被騙。更務實的做法通常是：

- 把它當成「排序問題」：看已知正例是不是更容易被排到前面
- 對 `p_std` 高的樣本做抽查/送驗/人工補標註，逐步把 `U` 轉成真實標籤

---

# 8. 後續怎麼把它做得更可靠

1. 能補就補真實負例
2. 把 `p_std` 當成「優先處理清單」的依據：先針對不確定的地方補資料，模型會越來越可靠
3. 對外溝通時，清楚講「資料知道什麼、不知道什麼」：避免把「沒有紀錄」誤說成「不通過」
