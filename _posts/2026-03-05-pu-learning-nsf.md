許多專案起初被視為標準二元分類（pass=1、fail=0），進行到一半才發現：資料中根本沒有「真實負例」，只有「確定正例」與「其餘未知」。這種設定就是 **PU Learning（Positive-Unlabeled Learning）**。

本文會先以簡單易懂的方式說明 PU Learning 及其常見原因，再列舉幾個實際案例；最後分享我分析「認證資料」時遇到的問題，示範如何將 PU 思維運用於真實資料。

---

# 1. 什麼是 PU Learning

PU Learning 的核心在於資料只有兩種狀態：

- `P`：確定為正例（positive），例如「確定通過某項認證」或「確定是詐騙」。
- `U`：未標註（unlabeled），例如「尚未被標註是否通過」或「尚未被確認是否詐騙」。

`U` 不是負例，其中通常混合兩種樣本：

- 真正的正例：實際上是正例，但尚未被標註。
- 真正的負例：實際上確實是負例。

因此 PU Learning 和一般監督式二元分類最大的差異是：

- 監督式學習：同時擁有「正例」與「真實負例」。
- PU Learning：只有「正例」與「未知」。

這項差異看似只在於標籤，影響卻很大：如果將 `U` 直接當作負例訓練，就等同在資料中加入大量「偽陰性」（false negatives），使模型學到偏誤規則，連機率輸出也可能失真。

![監督式二元分類 vs PU Learning 示意圖](/assets/images/260305/pu-supervised-vs-pu.svg)

_圖：PU 的關鍵在於 `U` 不是「0」，而是一組混合正例與負例的未知樣本。_

# 2. PU Learning 的典型例子（為什麼它很常見）

PU 之所以常見，是因為**正例通常較容易獲得確認，所謂負例往往只是尚未被確認的樣本**。

以下是幾個容易理解的例子：

- 反詐騙：`P`=已確認的詐騙交易；`U`=其他交易（多數不是詐騙，但也可能有遺漏）。
- 疾病篩檢：`P`=已確診者；`U`=未接受檢查或尚未確診者（不代表健康）。
- 推薦與偏好：`P`=按讚、收藏或購買；`U`=未互動的內容（可能未曾看到，也可能不感興趣）。

如果直接將這些問題中的 `U` 全部當作負例（`0`）訓練，常見後果包括：

- 模型將「未被標註」誤認為「負例特徵」，使決策邊界產生偏誤。
- 機率輸出變得不可靠，不能直接視為真實的 `P(y=1|x)`。
- 指標看似良好，實際用於決策時卻容易出錯。

---

# 3. 一個很常見的「認證資料」陷阱：只有通過紀錄，沒有不通過

接下來介紹我實際遇到的案例。先說明背景，以免後續的專有名詞讓人難以掌握問題脈絡。

以 NSF 這類第三方認證資料為例，通常可以取得「哪些產品通過了哪些項目」的清單，卻不一定能取得「哪些產品未通過哪些項目」的資料。

我當時取得一份整理過的資料，內容包括：

- 某些產品在特定認證項目上有公開的通過紀錄。
- 對於沒有出現通過紀錄的項目，無法確認其原因。

重點在這句：**沒有通過紀錄，不等於不通過。**

![只有通過紀錄的認證資料：空白通常代表未知，不等於不通過](/assets/images/260305/cert-records-unknown-not-fail.svg)

_圖：如果資料來源只記錄「通過」，空白欄位多半代表未知（U），不能直接視為不通過（N）。_

沒有通過紀錄可能代表：

- 產品根本沒有申請該項認證。
- 產品已送件，但結果並非通過。
- 產品已通過，但資料並未收錄，例如來源缺漏或更新不同步。
- 資料整理過程有所遺漏。

換句話說，在這類資料中：

- `P`=「確定有通過紀錄」（正例）
- `U`=「其餘狀態均無法確認」（未標註）

這就是典型的 PU Learning 情境。

---

# 4. 為什麼「把缺漏都當作不通過」會導致錯誤結果

許多人的第一個直覺，是將沒有通過紀錄的資料視為 fail=0，再直接套用一般二元分類。

這個做法不只「不夠精準」，更代表**標籤語意從一開始就錯了**。將「未知」視為「不通過」，等同以錯誤答案訓練模型：

- 模型實際學到的是判斷「是否被記錄」，而不是「是否通過」
- 資料中會出現大量偽陰性，使模型學到偏誤規則
- 評估指標也容易產生誤導：由於 `U` 通常遠多於 `P`，模型只要偏向預測 0，就能得到看似不錯的 accuracy

由此可見，這不是調整 0 或 0.5 權重就能解決的問題，而是必須正視資料本質上屬於 PU。

---

# 5. 面對 PU 資料，可以採取哪些做法

以下以容易理解的方式，將常見做法整理成三類，方便讀者對照自己的情境。

## 選項 A：重新定義問題（不將未知資料視為負例）

將任務從「通過或不通過」改為更符合資料事實的目標，例如：

- 「是否有通過紀錄」（recorded vs. not recorded）

優點：

- 標籤語意正確，因為資料真正能確認的只有「是否有紀錄」

缺點：

- 這不等於 pass/fail
- 對外溝通時必須謹慎：只能說「較接近有紀錄產品的特徵」，不能直接宣稱「一定通過」

## 選項 B：補齊真正的負例（最根本，但成本最高）

如果能取得每項產品在各認證項目上的真實結果：

- pass=1
- fail=0

便可以回到一般監督式分類，評估結果也會更加可靠。

但在實務上，這通常需要取得外部資料、進行人工補標註，或負擔實驗與送驗成本。

## 選項 C：使用 PU Learning 方法（在只有正例的前提下建立可用模型）

PU 方法很多，本文只介紹一種容易理解、也經常作為 baseline（基準方法）的做法：**PU Bagging**。

---

# 6. 我最後採用的做法：PU Bagging（同時計算不確定性）

PU Bagging 的直覺是：既然 `U` 中混合了正例與負例，就不應一次將所有 `U` 都視為負例，而應採取「多次抽樣、多次訓練，最後取平均」的方式。

做法概念如下：

1. 每次訓練都保留所有正例 `P`
2. 從 `U` 隨機抽取一小部分，暫時當作偽負例（pseudo-negative）進行訓練
3. 重複多次，取得多個模型的預測結果
4. 將預測結果取平均作為最終分數，並以分散程度表示「不確定性」

可以將它想像成：面對同一道答案不確定的考題，請許多同學根據不同假設作答；最後不只查看平均答案，也觀察大家的分歧程度。

在這個案例中，最後會得到兩項實用的輸出：

- `p_mean`：平均分數，可理解為「與正例的相似程度」或「接近已有通過紀錄產品的程度」
- `p_std`：分散程度，可理解為「不確定性」或「分數的穩定程度」

![PU Bagging：多次抽樣訓練，取平均分數並用標準差表示不確定性](/assets/images/260305/pu-bagging-mean-std.svg)

_圖：Bagging 會以不同樣本進行多次訓練，將平均值作為分數，並以分散程度表示不確定性。_

# 7. 如何解讀結果及其限制

## 7.1 最重要的一句話：這不是在學「不通過」

由於資料中沒有真實負例，`p_mean` 不能解讀為「通過機率」，而比較接近：

- 衡量樣本與已知通過紀錄產品之相似程度的分數

如果直接以此宣稱產品「一定通過」或「一定不通過」，便會誤解資料與分數的真正含義。

## 7.2 將不確定性（`p_std`）納入決策，比直接切分 0／1 更安全

實務上可以採用以下解讀方式：

- `p_mean` 高、`p_std` 低：較接近正例，且結果穩定
- `p_mean` 高、`p_std` 高：看似接近正例，但不確定性較高，建議送驗或人工確認
- `p_mean` 低、`p_std` 低：較接近非正例，且結果穩定

## 7.3 評估方式也必須相應調整

在缺乏真實負例的情況下，直接計算 accuracy 或 F1 容易得到誤導性的結果。較務實的做法包括：

- 將任務視為「排序問題」，檢查已知正例是否更容易排在前面
- 對 `p_std` 較高的樣本進行抽查、送驗或人工補標註，逐步將 `U` 轉換成真實標籤

---

# 8. 如何進一步提升可靠性

1. 優先補充真實負例。
2. 將 `p_std` 作為安排處理優先順序的依據，先針對不確定性較高的樣本補充資料，逐步提升模型可靠性。
3. 對外溝通時，清楚說明資料能確認與無法確認的資訊，避免將「沒有紀錄」誤述為「不通過」。
